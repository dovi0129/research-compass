## D-002. FR-03(연구지원 추세)의 구현 축을 D1 선정년도로 확정

**근거:** D-001 확인사항 ②.

제출 사업계획서의 "연구지원 추세 분석"을 **D2 의 분야별 선정횟수 시계열로 해석하면 구현 불가능**하다.
D1 에는 `선정년도`(및 별개로 `사업년도`)가 있으므로, 연도 축 분석은 **D1 의 선정연도별 수록 레코드 분포**로만 제공한다.
이는 명세 8.1이 이미 규정한 기본 기능과 일치하므로 설계 변경이 아니라 **축의 확정**이다.

표기 제약(명세 8.2 유지):
- 차트 제목은 `다운로드한 자료 내 선정연도별 수록 분포`
- 국가 전체 연구지원 현황이라고 표기하지 않는다
- 계속과제 반복 수록 가능성이 있으므로 해당 연도의 신규 선정 건수로 해석하지 않는다
- `comparable_trend` 는 `disabled` 로 두고 성장률·증가 분야 문구를 출력하지 않는다

## D-006. 「탐색이 적은 분야」를 D2 만으로는 관측할 수 없다 — 발표 핵심 쟁점

**확인된 사실:** D2 의 선정횟수 최소값이 **1** 이다. 0건인 분야가 한 행도 없다.

즉 이 데이터는 *전체 연구분야 목록*이 아니라 **선정 실적이 있는 분야만 모은 목록**이다.
과학기술표준분류 전체 코드 수는 851개보다 많으므로, **한 번도 선정되지 않은 분야는 이 파일에 애초에 존재하지 않는다.**

제출 사업계획서의 핵심 문구는 "상대적으로 탐색이 적은 인접 연구영역"이다.
현재 자료로 말할 수 있는 것은 **"선정된 분야들 중 상대적으로 적게 선정된 분야"** 까지이며,
**"아무도 하지 않은 분야"** 는 말할 수 없다. 이 둘을 구분해서 표현하지 않으면 근거보다 강한 주장이 된다.

**선택지:**

| 안 | 내용 | 판단 |
|---|---|---|
| A | 현재 자료 범위 그대로 가되 UI·발표 문구를 "선정 실적이 있는 분야 중 상대적 하위"로 정확히 제한 | 추가 자료 불필요. 명세 9.5 준수. **기본안** |
| B | 공식 과학기술표준분류 전체 코드표를 확보해 D2 와 차집합을 구해 '선정 0건 분야'를 도출 | 제출안의 주장에 훨씬 가까워짐. 단 **데이터 추가**이므로 명세 21.3 에 따라 변경안 승인 필요 |

B 를 채택하면 발표의 차별성 주장이 실제 데이터로 뒷받침된다. 통합 담당자 결정 필요.

## D-007. 명세 9.2 의 「하위 25%」 규칙은 이 데이터에서 변별력이 없다

**확인된 사실:** 선정횟수 분포가 심하게 치우쳐 있다. 1회가 353개, 2회 162개, 3회 92개 … 최대 56.
따라서 `q25 = 1` 이고, **q25 이하 조건을 만족하는 분야가 전체의 41.5%(353개)** 다.

명세 9.2 는 "동률이 많으면 하위 25% 기준을 만족하는 분야 비율이 25%를 넘을 수 있다"고 이미 예상했고,
"실제 비교 대상 수와 기준값을 표시하고 숨기지 않는다"고 규정했다. 그 상황이 실제로 발생했다.

**결론:** 하위 25% 단일 규칙만으로 후보 3개를 뽑으면, 사실상 "관련도 상위 3개"를 뽑는 것과 같아진다.
후보 규칙은 G3 에서 재설계가 필요하며, 최소한 다음을 함께 표시해야 한다.

- 비교 집단 크기와 기준값 (`comparison_size`, `comparison_cutoff`)
- 기준을 만족하는 분야가 비교 집단의 몇 %인지
- 동률 분야 수

명세 9.5 가 금지한 종합 기회 점수(`관련도 × 신규성 × 성장성`)를 만들어 이 문제를 우회하지 않는다.

## D-008. 기준기간 충돌의 정황 근거 — 2025년 쪽이 유력하나 미확정

**대조:** D2 선정횟수 **합계 2,909** vs D1 연도별 레코드 수

| 연도 | D1 레코드 | D2 합계와의 차이 |
|---|---|---|
| 2023 | 5,617 | −2,708 |
| 2024 | 3,302 | −393 |
| **2025** | **2,869** | **+40** |

2025년과의 차이가 +40 (1.4%)으로 압도적으로 가깝다. 한 과제가 복수 분야에 계상될 수 있다는 점을 감안하면
**컬럼명의 `2025년` 이 맞고 등록 페이지 설명문의 `2023년` 이 갱신되지 않은 문구일 가능성이 높다.**

**그러나 이는 정황 근거이지 공식 확인이 아니다.** 명세 4.2·9.2(`require_verified_period: true`)에 따라
`period_status` 는 `conflicting` 을 유지하고 `field_counts` 와 `opportunity_candidates` 는 `disabled` 로 둔다.

**닫는 방법:** 공공데이터포털 문의 또는 한국연구재단 담당 부서 확인.
확인되면 `field_counts` → `verified` 가 되고 `opportunity_candidates` 의 게이트 하나가 열린다.
**대면 발표 전에 반드시 처리해야 할 1순위 항목이다.**

## D-009. ~~D2 중심분야코드는 두 개의 분류체계가 섞여 있다~~ — ⚠️ **정정됨 (D-013 참조)**

> **이 항목의 결론은 틀렸다.** `HA`~`HE`, `SA`~`SI` 는 별도 분류체계가 아니라
> **2018년 국가과학기술표준분류체계에서 실제 사용된 코드**다. 아래 수치는 사실이지만
> 그 해석("다른 분류체계")은 D-013 에서 뒤집혔다. 기록 목적으로 남긴다.

### (원문) D2 중심분야코드는 두 개의 분류체계가 섞여 있다 (P1 결과)

**대조:** `한국과학기술기획평가원(KISTEP)_과학기술표준분류_20251231` (2,807행, 소분류 2,807개, sha256 `b9b2fb688f7832e8…`)
KISTEP 은 **보조 공공데이터**다. NRF 데이터를 대체하지 않으며 코드·계층 복원에만 쓴다.

### 결과

| 지표 | 값 |
|---|---|
| 코드 정확 일치 (전체) | 109/851 = **12.81%** — 게이트(95%) **미달** |
| 코드 정확 일치 (KISTEP 체계 내 한정) | **98.20%** (109/111) — 게이트 통과 |
| ↳ 해당 범위가 D2 에서 차지하는 비중 | **13.0%** (111/851행) |
| 명칭 완전 일치 (코드 일치 건 중) | 93/109 = 85.32% |
| 명칭 정규화 후 일치 | 95/109 = **87.16%** |

### 무엇이 밝혀졌나

D2 의 `중심분야코드` 는 전부 6자리 `AA9999` 형식이지만, **앞 2자리 접두가 두 무리로 갈린다.**

- **KISTEP 체계에 속하는 접두 19종** (`EA`~`EI`, `LA`~`LC`, `NA`~`ND`, `OA`~`OC`) — 111행.
  이 범위에서는 코드가 98.2% 일치하고 명칭도 87% 일치한다. **대조 자체는 신뢰할 수 있다.**
- **KISTEP 체계에 없는 접두 14종** (`HA`~`HE`, `SA`~`SI`) — **740행, D2 의 87.0%**.
  국가과학기술표준분류에는 인문사회가 `HF`(인문학) `HG`(사회과학) `HH`(문화예술체육학)로 들어 있는데,
  D2 는 `HA`~`HE`, `SA`~`SI` 를 쓴다. **다른 분류체계다.**

이는 D1 의 구성과 정확히 부합한다. D1 은 11,788건 중 10,370건(88.0%)이 `학술·인문사회사업` 이다.

### 판정

- 전체 게이트 미달이므로 **KISTEP 만으로 D2 전체의 미탐색 영역을 정의할 수 없다.**
- 억지 매칭을 만들지 않는다. 접두가 다른 체계를 이름 유사도로 잇지 않는다. (명세 4.3-4)

## D-010. `unobserved` 산정 범위와 의미

- 범위: D2 가 실제로 사용하는 KISTEP 대분류 19종의 하위 소분류 **1,717개**

- → **unobserved 1,608개**

**의미의 한계 — 발표에서 반드시 구분해야 한다:**

| 말할 수 있는 것 | 말할 수 없는 것 |
|---|---|

`unobserved` 는 "실제로 선정이 없었는지" 와 "애초에 수록 대상이 아닌지" 를 **구분하지 못한다.**
D2 의 87% 를 차지하는 인문사회 코드에 대해서는 참조 코드표가 없으므로 **unobserved 를 산정하지 않는다.**

  라벨한 뒤 `analyze-tau` 의 정밀도 곡선으로 정한다. 그때까지 `project_relevance_threshold: null` 유지.
- 사람 스팟체크 30건을 발표 전 수행하여 AI–사람 일치율을 함께 보고한다. 이것이 없으면 "AI가 AI를 채점" 비판에 답이 없다.

## D-019. tau 심층 표본 결과 (G2-B1) — 상대 점수(margin)가 가장 깨끗함, **tau 는 아직 미확정**

**실행:** 연구실 서버 Lab33(RTX 5090, torch 2.11.0+cu128)에서 `make-tau-probe` → 개발 질의 5개 × (순위 6·7·8·9·10·15·20·30·50·100·200·500 + 무작위 3) = **75건**.
라벨러는 **Claude Sonnet 5개 인스턴스(1차, 사람 검토 전)**, 질의당 1개씩 병렬. 각 인스턴스는 **자기 질의의 블라인드 항목 파일 1개만** 열었고
`pool_key_tau_dev.csv`(순위·점수)는 구조적으로 격리했다. 라벨 분포: 2=10, 1=31, 0=33, U=1.
산출물: `evaluation/label_sheet_tau_dev.llm.csv`, `evaluation/pool_key_tau_dev.csv`, `evaluation/results/tau_curve_dev.json`.

### 점수 공간별 곡선 (개정안 6.2)

| 공간 | 규칙 2 의 tau | 그 지점 P(2∪1) | 구간별 곡선 형태 |
|---|---|---|---|
| `s_sem` (절대 코사인) | 0.46 | 0.73 | 전이구간이 **비단조** — [0.48,0.50)=0.33 → [0.50,0.52)=0.00 → [0.52,0.54)=0.40 |
| **`margin`** (s_sem − p99(q)) | −0.04 | 0.74 | **0 에서 한 번에 끊긴다** — 0 미만 12개 구간이 전부 관련 0.00 |
| `rank` | 200위 | 0.74 | 단조에 가깝지만 게이트로 쓰면 질의마다 **고정 개수**를 반환한다 |
| `s_rr` | — | — | 재정렬기 미적용 단계 — G2-B4 에서 측정 |

### 핵심 실측 (`margin` 부호별 라벨 교차표)

| | 라벨 0 | 라벨 1 | 라벨 2 |
|---|---|---|---|
| `margin < 0` (p99 미만) | **24** | **0** | **0** |
| `margin ≥ 0` (p99 이상) | 9 | 31 | 10 |

- 표본의 **관련 항목 41건 전부가 `margin ≥ 0`** 이다 (최소 +0.0067). p99 아래에서 관련 항목이 한 건도 나오지 않았다.
- 같은 표본에서 `s_sem ≥ 0.46` 은 비관련을 **15건** 통과시키고 `margin ≥ 0` 은 **9건** 통과시킨다. margin 이 엄격하게 우세하다.
- 질의별 p99 가 **0.4697 ~ 0.5866** 으로 흩어져 있다. 절대 코사인 tau 는 질의 간 의미가 달라진다 — D-016 의 점수 압축 관찰과 일치.

### 결정

1. **점수 공간은 `margin` 을 우선한다.** 근거는 위 교차표와 질의별 p99 산포. 개정안 6.3-1 의 "한 지점에서 뚝 떨어지는 공간" 조건을 유일하게 만족한다.
2. **tau 는 확정하지 않는다.** `project_relevance_threshold: null` 을 유지한다. 확정을 막는 두 가지가 실측으로 드러났다.
   - **경계가 표본 격자에 걸려 있다.** `margin ≥ 0` 은 이 표본에서 `sem_rank ≤ 100` 과 **완전히 동일한 분할**이다(margin≥0 은 순위 6~100, margin<0 은 200위 이상). 표본에 100위와 200위 사이 항목이 없어서, 코퍼스 상위 1% 경계(118위) 부근에서 경계를 더 좁힐 수 없다. **따라서 이 증거로는 `margin` 과 `rank` 를 구분할 수 없다.**
   - **표본이 순위 층화 표본이다.** 순위 격자로 뽑았으므로 특정 점수 구간의 균일 표본이 아니다. 따라서 `P(tau)=0.82` 를 "기준값을 넘긴 결과의 82%가 관련"이라는 **무편향 추정치로 읽을 수 없다.** 보고서에 이 사실을 병기한다.
3. **개정안 6.3-2 의 문자 그대로의 결과(−0.04)를 채택하지 않는다.** margin 공간에서 −0.04 와 0.00 사이에는 관련 항목이 0건이므로, −0.04 는 recall 이 같으면서 정밀도만 낮은(0.74 vs 0.82) **열등한 절단점**이다. G2-B4 의 잠정 후보는 **`margin`, tau = 0.00** 으로 기록하고, 규칙을 문자대로 적용하지 않은 사유를 여기 남긴다.
   → 개정안 6.3-2 는 "가장 낮은 t" 대신 **"정밀도·포용성에서 지배되지 않는 가장 낮은 t"** 로 읽어야 한다. B5 보고서에 규칙 보정으로 명시한다.
4. **엄격 기준(라벨 2)으로는 어떤 공간에서도 tau 를 세울 수 없다.** `margin ≥ 0` 에서 P(2)=0.20 이고, P(2)≥0.5 는 margin ≥ 0.12(n=6)에서야 나온다. 게이트는 2∪1 기준으로만 정의한다.
5. **남은 확인:** ① G2-B3 재정렬기 → G2-B4 에서 `s_rr` 곡선과 비교, ② 순위 110~190 구간 보강 표본(질의당 6건 = 30건)으로 경계를 좁히는 것이 유효 — 채택 시 별도 결정으로 기록, ③ 사람 스팟체크 30건(2/1 경계)은 발표 전 필수.

**부수 확인 (서버 bootstrap):** `torch 2.6.0+cu124` 는 RTX 5090(sm_120) 커널이 없는데도 `torch.cuda.is_available()` 이 `True` 를 반환했다.
`bootstrap.sh` 의 설치 순서(`torch` cu128 → `pip install -e .[search,dev]`)가 PyPI 기본 휠로 되돌려놓은 것이 원인이다.
extras 를 먼저 설치하고 장치용 휠을 마지막에 덮어쓰도록 순서를 바꾸고, `sm_120 in torch.cuda.get_arch_list()` 검사를 추가했다.
`BAAI/bge-m3` 에는 `model.safetensors` 가 없어(루트 가중치는 `pytorch_model.bin` 뿐) 하드코딩된 파일명이 404 로 bootstrap 을 중단시키던 문제도 저장소 파일 목록에서 고르도록 고쳤다.

## D-020. 하이브리드(RRF) 채택 판정 (G2-B2) — **미달. 기본값 off**

**측정:** `evaluate-conditions --conditions A,B,C`. 같은 라벨 시트로 세 조건을 채점했다(개정안 9.1).
라벨은 기존 Top-5 풀 + tau 심층 표본 + 증분 10건(조건 C 의 Top-5 에 새로 들어온 항목, Sonnet 블라인드 1차).
설정: `rrf_k=60`, `candidate_pool=100`(방식별 상위 50 합집합).

| 조건 | dev 엄격 P@5 | dev 완화 P@5 | test 엄격 P@5 | test 완화 P@5 |
|---|---|---|---|---|
| **A** 의미 단독 | **0.44** | **0.96** | **0.40** | **0.92** |
| B 어휘 단독 | 0.24 ~ 0.28 | 0.76 ~ 0.80 | 0.22 ~ 0.26 | 0.78 ~ 0.82 |
| **C** RRF | 0.36 ~ 0.40 | 0.92 ~ 0.96 | 0.36 | 0.90 |

**판정: 채택하지 않는다.** 개정안 3절의 조건은 "dev·test 모두에서 C ≥ A" 인데 **두 분할 모두에서 C < A** 다.
엄격 기준으로 dev −0.04~−0.08, test −0.04, 완화 기준으로도 dev ≤, test −0.02 다.

**단일 질의 효과가 아니다.** 질의 15개 중 **악화 5 · 개선 2 · 동일 8**, 방향이 두 분할에서 일관된다.

| 분할 | 악화 | 개선 | 동일 |
|---|---|---|---|
| dev (5) | dev02 0.80→0.60, dev04 0.20→0.00 | — | 3 |
| test (10) | test04 0.40→0.00, test07 0.60→0.40, test08 0.20→0.00 | test05 0.40→0.60, test06 0.20→0.40 | 5 |

**해석.** D-017 은 두 방식의 상위 결과가 거의 겹치지 않는다(9/50)는 것을 근거로 "결합하면 이득일 가능성"을 제시했다.
실측 결과는 반대다. **겹치지 않는다는 것은 어휘검색이 다른 관련 과제를 찾아낸다는 뜻이 아니라, 다른 무관한 과제를 찾아낸다는 뜻이었다.**
엄격 P@5 가 0.22~0.28 인 방식을 RRF 로 동등 가중하면 Top-5 에 비관련 항목이 밀려 들어온다.

**결정**
1. `config/default.yaml` 의 `retrieval.hybrid: false` — **기본값 off**. 코드 경로(`fusion.py`)는 유지하고 `SearchRequest.hybrid=true` 로 켤 수 있다. 켜면 `HYBRID_DISABLED_BY_EVAL` 경고가 응답에 붙는다.
2. 어휘 검색은 **비교 baseline 으로만** 남긴다(명세 18.5). 검색 경로에서 제거하지 않는다 — 조건 B 수치를 계속 보고해야 한다.
3. **가중 RRF 는 시도하지 않는다.** dev 로 가중치를 맞추고 test 로 검증하면 표본이 15질의뿐이라 과적합이고, 명세 18.1 이 평가 질의로 설정을 조정하는 것을 금지한다. 시도했다면 그 사실과 재라벨링 비용을 함께 보고해야 한다.
4. 발표에서 말할 수 있는 것: **"하이브리드 검색을 구현해 측정했고, 이 데이터에서는 손해였으므로 껐다. 근거 파일이 있다."** 이것이 "근거 없는 기능은 켜지 않는다"의 실물 사례다.

**부수 확인:** 조건 A·B 수치가 D-017(0.44/0.96, 0.24~0.28/0.76~0.80, 0.40/0.92, 0.22~0.26/0.78~0.82)과 **완전히 일치**한다.
새 파이프라인(`search.py`)이 기존 평가를 재현한다는 회귀 확인으로 쓴다.

`evaluation/label_sheet_{dev,test}_incr.llm.csv`.

## D-023. 재정렬기 채택 판정 (W4 / G2-B3) — **E 채택. 기본 경로 = 의미검색 + 재정렬(N_r=20)**

**측정:** `evaluate-conditions --split dev|test --conditions "A,B,C,D,E,E'" --used-for-selection`.
증분 라벨 38건(Sonnet 4개 병렬, 블라인드, 분할·조건·순위 비노출)을 추가해 **미라벨 0건**으로 만든 뒤 채점했다.
라벨 총계 dev 121건 / test 127건, 출처 전부 `llm`. 실행 환경: 노트북 CPU, 재정렬기 `953dc6f6…` float32.

| 조건 | dev 엄격 P@5 | dev 완화 | test 엄격 P@5 | test 완화 | warm 평균/최대 |
|---|---|---|---|---|---|
| **A** 의미 단독 | 0.44 | 0.96 | 0.40 | 0.92 | 0.13~0.14초 / 0.31초 |
| B 어휘 단독 | 0.24~0.28 | 0.76~0.80 | 0.22~0.26 | 0.78~0.82 | — |
| C RRF | 0.36~0.40 | 0.92~0.96 | 0.36 | 0.90 | 0.10~0.13초 |
| D RRF + 재정렬 | 0.56 | 1.00 | 0.40~0.50 | 0.78~0.88 | 2.15~2.47초 |
| **E 의미 + 재정렬 N_r=20** | **0.56** | **1.00** | **0.44~0.48** | 0.90~0.94 | **2.23~2.68초 / 4.13초** |
| E′ 의미 + 재정렬 N_r=50 | 0.52 | 1.00 | 0.38~0.42 | 0.86~0.90 | 5.69~7.29초 / **9.80초** |

**판정: E 를 채택한다.** 개정안 5.5 의 조건을 **dev·test 둘 다** 만족한다.

- 엄격 P@5 가 A 대비 상승: dev **+0.12**(0.44→0.56), test **+0.04~0.08**(0.40→0.44~0.48). test 는 하한도 A 를 넘는다.
- 어휘 baseline(0.22~0.28)을 크게 넘는다.
- warm 이 5초 이내: 평균 2.23~2.68초, 최대 4.13초.
- **E′(N_r=50)는 기각.** 두 분할에서 E 보다 낮고 test 최대 9.80초로 5초 목표를 넘는다. `top_n=20` 유지.
- D(RRF+재정렬)는 dev 에서 E 와 동률이지만 test 에서 낮다(0.40~0.50 vs 0.44~0.48, 완화 0.78~0.88 vs 0.90~0.94). D-020 의 `hybrid=false` 를 뒤집을 근거가 아니다.

**질의별 변화** — 단일 질의 효과가 아닌지 확인했다.

| 분할 | 개선 | 동일 | 악화 |
|---|---|---|---|
| dev (5) | 1 (dev05 0.20→0.80) | 4 | 0 |
| test (10) | 4 (test04·06·09·10) | 4 | 2 (test01 1.00→0.80, test03 0.80→0.60) |

**dev 의 상승은 사실상 질의 1개에 의존한다.** dev 가 5개뿐이라 이 값 하나로 채택을 정할 수 없었고,
test 에서 개선 4·악화 2 로 분포가 넓게 나온 것이 판정의 실질 근거다. 반대로 test 에서 최상위 질의 2개가
악화한 것도 숨기지 않는다 — 재정렬기가 이미 좋은 순위를 흔드는 경우가 있다.

### 채택했지만 "검증됨" 이 아니다

v2 §2.2·§17.3~17.4 에 따라 아래를 명시한다.

1. **라벨이 LLM 1차뿐이다.** 사람 스팟체크 30건(2/1 경계) 전에는 P@5 를 "검증됨"으로 표기하지 않는다.
   같은 모델의 병렬 에이전트 4개를 **사람 평가자 4명으로 쓰지 않는다.** 시트의 `label_source` 는 전부 `llm` 이다.
2. **dev·test 둘 다 `used_for_selection: true` 다.** test 를 보고 E 를 골랐으므로 test 는 더 이상 미사용 검증셋이 아니다.
   D-020(하이브리드 off)에서도 이미 test 를 썼다. 최종 확인에는 **새 질의 5개 이상**이 필요하다(v2 §17.4).
3. **warm 은 노트북 CPU 단일 환경 측정이다.** 질의별 분포(평균·최대)를 함께 기록했고, 한 번의 측정으로
   일반적인 응답시간을 주장하지 않는다(v2 §7.4).
4. `U` 라벨이 test 에 2건 남아 상·하한이 벌어져 있다(0.44~0.48). 확정값이 아니라 구간이다.

**설정 반영:** 실행 기본값은 `retrieval.hybrid: false` + `rerank.enabled: true` + `rerank.top_n: 20` 조합이
그대로 E 를 만든다. 기록용으로 `retrieval_policy.default_engine: Retrieval-E` 와 근거 파일 경로를 넣었다.
근거가 무효화되면 `unresolved_default: semantic_only` 대로 A 로 되돌린다.

| 비교 단위 = 요소 × 선택 과제, 요소 없으면 자동 분해 안 함 (§9.1) | `build_matrix(elements, refs)` — 요소가 없으면 빈 목록. 화면은 선택 제목만 보여주고 요소 입력을 안내 |
| 인용 = `title_raw[start:end] == quote`, 0-based 코드포인트, 끝 미포함, 원문 UTF-8 SHA-256 (§9.5) | `EvidenceQuote.problems()` 가 세 조건을 검사. 비-BMP 문자로 코드포인트 인덱스 시험 |
| 정규화 비교는 원문 위치를 정확히 복원할 때만 (§9.3) | `_norm_map` 이 정규화 문자마다 원문 인덱스를 보존 → 복원 구간을 다시 정규화해 요소와 같아야 인용. `㈜`→`(주)` 처럼 복원이 안 되는 매칭은 인용을 만들지 않는다 (시험) |
| 부분 단어 ≠ 요소 확인 (§9.3-4) | 요소 전체 문자열만 찾는다. 부분 단어가 있으면 `limitations` 에 "부분 단어 … 는 있지만 전체 표현이 아니다" 를 적고 `needs_review` 유지 |
| 부정·비교 문맥 (§9.7) | `강화학습을 사용하지 않는 …` 도 `expression_found` 다. 생성 문장은 "표현이 제목에 있다" 까지만. `FORBIDDEN_PHRASES`("사용을 확인했다"·"다루지 않았다"·"연구된 적이 없다"·"독창적이다"·"동일 연구다" …) 를 시험이 검사 |
| `not_confirmed_in_title` 은 사용자 검토로만, 인용 없음 (§14.4) | `review_not_confirmed()` 만 만든다. `validate()` 가 `reviewer_kind != user` 나 인용 존재를 위반으로 본다 |
| 자동 매칭은 `unreviewed` 로 시작, `confirmed` 는 사용자만 | `observe()` 는 항상 unreviewed. `review_confirm()` 은 인용이 없으면 `EvidenceError`. `model_proposal` 자동 confirmed 는 검증 위반 |
| 사용자 해석은 승격되지 않는다 (§9.4) | `set_interpretation()` 은 `user_interpretation` 만 바꾼다. 메모에서 "사용자 검토 의견" 별도 열 |
| 요소 revision·원문 해시가 바뀌면 이전 확인 재사용 금지 | `observation_id` 에 요소 revision 이 들어간다. `merge_reviews()` 가 같은 id·같은 해시만 유지, 해시가 다르면 `stale`, 요소가 바뀐 이전 검토는 `stale` 목록으로 |

**다음 탐색·확인 (§10).** `propose()` 는 §10.2 규칙 순서로 최대 3개. 근거는 ws 의 요소·선택·관측·실행 이력·사용자 부족 표시·
사용자가 고른 분야명**만**. 억지로 채우지 않는다(근거 없으면 빈 목록, 시험). "방법 관점만 탐색" 은 **원래 주제(full) 검색을 제외한** 요소 기반
관점 집합이 `{method}` 인 경우로 해석했다. 상세 원문 연결이 없으므로 `inspect_project_detail` 문장은 "상세 자료 확인 필요" 로만 쓴다.
"검색문 미리보기" 는 관점 패널의 검색문 칸을 채우기만 하고 실행은 사용자가 누른다.

**메모 (§11).** `memo.build(snapshot, observations, next_actions)` → Markdown + JSON. 확정 영역에는 **사용자 검토가 있고 인용이 유효하고 stale 이 아닌**
관측만 들어간다(`is_settled`). 미검토 자동 발견·거부·stale·인용 검증 실패는 "아직 확인하지 못한 사항" 에 사유와 함께. 선택이 없으면
§11.4 문장을 그대로 쓴다. `[E#]` 는 메모 내부 번호. 같은 snapshot 이면 `generated_at` 외에는 결정적(시험). Markdown escape 는 서식·HTML·표 구분 문자만
하고 식별자는 코드 스팬으로 감싼다(처음엔 `-`·`_` 까지 escape 해 `Retrieval\-E`·`run\_…` 이 됐다 — 시험이 잡았다). URL 은 https 만. 로컬 절대 경로가 있으면 `MemoError`.

**화면.** 세 영역이 결과·비교함 아래에 실제 내용으로 들어갔다. 검토 상태는 세그먼트 컨트롤(미검토 / 관련 있음(확인) / 연결 거부 / 제목에서 확인 안 됨)
+ 검토 의견 + (미검출 셀) 원문 구절 입력 → "인용 추가". 규칙 위반(인용 없이 확인)은 콜백에서 되돌리고 메시지를 보인다.
발견 구간은 `<mark>` 로 강조(원문 escape 후 코드포인트로 자름). 메모는 미리보기 + Markdown/JSON 내려받기, "연구주제·메모가 파일에 포함됩니다" 안내.

**남은 것.** 실사용자 3명 UX-L vs UX-W(W5), 제한 기능표·재현 실행·최종 인계(W6), 사람 스팟체크 30건, 새 질의 5개, 시연 기기 응답시간.

## D-028. W5 — UX-L 비교 조건 구현과 사용자 평가 양식 (사용자 평가는 미실시) (2026-09-09)

**한 것:** 비교 대상 조건 **UX-L(목록 전용)** 을 `app.py` 에 구현하고, 진행 대본·기록 양식·판정 기준·작업 주제(실측)를
`reports/ux_study/` 에 준비했다. 시험 **9개** 추가 (`test_app.py` +6: UX-L 5 + 이력 회귀 1, `test_memo.py` +3: 자유 메모) → 총 **236개 통과**(노트북) · 서버 **212 + 1 skipped**.

**결정 1 — 조건을 화면 하나에 스위치로 둔다.** 별도 앱·별도 브랜치를 만들지 않는다.
`--ux l` (또는 `RESEARCH_COMPASS_UX=l`) 이면 관점 조절·비교함·제목 근거 비교표·다음 탐색·탐색 메모(구조화) 다섯 영역을 빼고,
같은 엔진·같은 스냅샷·같은 표시 건수(5, 최대 10)로 목록만 보여준다. 이유: 두 조건의 검색 경로가 갈라지면 비교가 UI 효과가 아니라
엔진 차이를 재게 된다. `test_both_conditions_search_the_same_way` 가 같은 주제에서 검색문·엔진·재정렬 적용·결과 순서가
같은지 검사한다.

**결정 2 — UX-L 을 약한 비교 대상으로 만들지 않는다 (§17.6).** 목록 조건에도
(a) `검색문 직접 고치기` — 실제 검색문을 고쳐 재검색(기록은 `user_edited`), (b) `자유 메모` + Markdown 내려받기,
(c) 필터·탐색 이력·점수 분포·원문·출처·분야명 찾아보기를 그대로 준다. 이 셋이 없으면 "작업공간이 낫다" 는 결론이
비교 대상을 깎아서 얻은 것이 된다. 자유 메모는 **두 조건 모두** 에 둔다 — 기록·반출 수단 자체가 조건 차이가 되지 않게 한다.

**결정 3 — 자유 메모 본문은 시험된 모듈에서 만든다.** `memo.free_memo(user_text, idea_text, generated_at)` 로 옮겼다.
머리말은 사실만(작성 시각·연구주제·자료 범위), 본문은 **사용자가 쓴 글 그대로**(escape 하지 않는다 — 사용자 자신의 파일이다).
자동 요약·해석·다음 행동을 만들지 않는다. 연구주제 줄만 표·서식 깨짐 방지로 escape 한다.

**결정 4 — 조건 이름을 화면에 쓰지 않는다.** `UX-L`·`UX-W` 는 `개발자용` 펼침에만 나온다(D-026 규칙). 참여자에게는
"화면 1 / 화면 2" 로만 말한다. UX-L 의 기능 상태표에서는 그 화면에 없는 4개 기능 행을 빼서, 없는 기능을 광고하지 않는다.

**고친 것 (실서버에서 발견) — 실행 직후 탐색 이력이 한 박자 늦게 나타났다.** 검색은 `render_history` 보다 아래 패널에서
실행되므로 그 render 에서는 이력 위젯이 이미 옛 목록으로 그려져 있었다. `execute()` 끝에 `st.rerun()` 을 넣어 실행 결과를
이력·상태칩·결과에 같은 응답에서 반영한다. **UX-W 에도 있던 문제다.** 회귀 시험
`test_second_search_shows_history_immediately` 를 넣고, `st.rerun()` 을 지우면 실패하는지 확인했다.

**작업 주제 (실데이터 실측, 노트북 CPU warm).** 자료 도메인 분포를 보고 **미리** 정한 4개 + 연습 1개.
결과가 좋은 주제만 남기지 않았다 — 상위 결과가 제목만 겹치는 주제(D: 딥러닝 의료영상, 1위−p99 = +0.113)를 일부러 남겼다.

| 주제 | 상위 5건 의미 유사도 | p99 | 1위−p99 | 지연 |
|---|---|---|---|---|
| 연습 대학생 진로 결정 자기효능감 | 0.624~0.695 | 0.544 | +0.151 | 4.9s (첫 실행) |

해석할 때 이 차이를 함께 적는다.

**하지 않은 것 — 사용자 평가.** 실사용자를 확보하지 못했다. §17.6 은 "사용자를 확보하지 못하면 설문·기록 양식만 준비하고
사용자 평가를 수행했다고 보고하지 않는다" 고 정한다. 따라서:

- 사용성 수치·비율·"탐색시간 N% 절감" 같은 문장을 **하나도 만들지 않았다**. `forms.md` 의 표는 빈 양식이다.
- 개발자 혼자 두 화면을 써 보고 결론을 적지 않았다 — 그것이 바로 개발자 친숙성 편향이다.
- 발표에서 UX-W 의 사용자 효용은 **"미확정"** 으로 말한다. 구현 성공과 사용자 효용을 분리해 보고한다(§19 W5 완료 조건).
- 실시하려면 3명 × 40분, `protocol.md` 를 그대로 따르면 된다. 결과는 `records.csv` + `forms.md` 4절 요약표.

**개인정보.** 기록 양식에 이름·소속·연락처·학번 칸을 두지 않았다. 참여자는 `P1`~`P3` 코드만. 녹화·녹음 없음.
참여자가 내려받은 메모 파일은 코드명으로 바꿔 **저장소 밖** 보관, 저장소에는 집계표와 익명 인용만 넣는다.

**남은 것.** W6(제한 기능표·재현 실행·최종 인계), 사람 스팟체크 30건, 새 질의 5개, 시연 기기 응답시간 재측정,
`client.showErrorDetails="none"`.

## D-029. 화면 전면 재설계 — 정보구조·레이아웃·라이트/다크 (계산 로직 변경 없음) (2026-09-10)

**요청:** 사용자 검토 — 콘텐츠 폭이 좁아 한국어 제목이 여러 줄로 꺾이고, 상자·펼침이 반복돼 개발자 대시보드처럼 보이며,
핵심 기능(탐색 관점·비교)이 묻혀 있다. 라이트/다크 지원, 개발자 정보는 뒤로. **검색·재정렬·감사·비교·메모의 계산 로직과
결과 의미는 바꾸지 않는다.** 출처·한계·불확실성 표시는 지운다.

**한 것:** `app.py` 를 표시 계층만 다시 썼다. `execute`·`apply_elements`·`refresh_observations`·검토 콜백·`memo.build` 호출 등
로직 호출부는 그대로다. 시험 **7개 추가**(`test_app.py` +6: 흐름 순서·관점 바로가기·비교표 문구·자유 메모 반출·카드 점수 표기·테마,
`test_memo.py` +1) + 관점 위젯 변경에 맞춘 시험 3곳 수정 → **243개 통과**(노트북). 서버는 재실행하지 않았다.

**결정 1 — 메인 흐름 8단계, 나머지는 접힘.** 머리말 → 연구주제 → **탐색 관점(항상 표시) + 실제 검색문** → 가까운 연구과제 70% + 비교함 30%
→ 선택한 과제 비교 → 다음 탐색·확인 → 탐색 메모(자유 메모 → 내보내기) → `추가 분석 및 데이터 정보`(관련 연구분야 · 데이터 범위와 제약 ·
검색 상세 분석 · 기능 및 검증 상태). 점수 분포 그래프·구성 그래프·실행 로그·모델 revision·manifest·기능 상태표는 모두 마지막 절로 옮겼고
**하나도 지우지 않았다**. `test_main_flow_order_and_perspective_always_visible` 이 절 순서를 검사한다.

**결정 2 — 관점은 `st.segmented_control`, 요소 3칸은 `세부 요소 조정` 접힘.** 관점별 뜻을 한 줄로 쓰되 검색문 구성 규칙
(`build_effective_query`: 방법 = 방법·접근 + 목표·질문, 대상·문제 = 대상·맥락 + 목표·질문)을 그대로 설명한다. 실제 검색문 칸은 항상 보이고

비교함 30%(유리 패널·sticky) → 선택한 과제 비교(표 + 확인 필요 요소 한 줄) → 탐색 메모(자유 메모 → Markdown/JSON) → 데이터·기능 정보(접힘 4개).
UX-L 은 같은 첫 화면·같은 카드에서 관점·비교함·비교표·구조화 메모만 없다.

**시각 체계 (계산 로직 무변경):** 팔레트 교체 — 라이트 `#F4F6F9`/`#0F172A`/강조 `#0E7C86`, 다크 `#0B0F17`/`#E7ECF3`/강조 `#3DD6C7`, 장식용
보조색 `#5B6CFF`/`#8B93FF` 는 로고·안내선 그라데이션에만. 배경에 아주 옅은 두 개의 radial 그라데이션(첫 화면에는 천천히 움직이는 블롭 2개).
**테두리 상자를 없애고** 카드·비교함·표를 `surface` 배경 + 낮은 그림자 + 16px 모서리의 표면으로(hover 시 살짝 떠오름). 비교함은 반투명 유리

`prefers-reduced-motion` 이면 모든 모션을 끈다. 참고한 방향: 2026 트렌드 글의 "차분한 인터페이스·절제된 유리감·다크 기본 + 반투명 패널",
Perplexity 류의 "가운데 검색칸 + 아래 예시 칩" 랜딩.

**Sonnet 리뷰(하위 에이전트, 캡처만 보고 12항목) 중 반영한 것:** 좁은 폭에서 상단바·관점 줄·결과/비교함 열을 세로로 쌓고 버튼 라벨 잘림 방지
(1000px 이하) · 관점 segmented 잘림(줄바꿈 허용) · 담기/근거 보기 버튼 위계 분리 · 비교함 sticky 가 실제로 붙지 않던 원인 수정(아래) ·
스텝퍼를 결과 순번 배지와 다른 형태(STEP n 텍스트)로 · 근거 팝오버의 식별자를 하위 그룹으로 · 예시 칩 말줄임 제거 · 막대 옆 ⓘ 툴팁.

아래 표로 이어진다. "결과 화면 배경 톤 단절" — 이미 같은 그라데이션을 옅게 쓰고 있어 그대로 둔다.

## D-032. 사용자 검토 6차 — 비교함 여백, 선택한 과제 비교를 레코드 사실 표로, 안내 뒷문장 삭제 (2026-09-10)

**요청(사용자):** (1) 비교함 빈 상자 안내 "비교할 과제 2~3개를 담아보세요" 는 사족, 상자 안 여백이 답답함. (2) 과제를 담으면 비교함 카드가 서로
붙어 답답함. (3) 요소를 넣지 않고 담으면 `선택한 과제 비교` 가 제목만 한 줄씩 보여 이상함. (4) "확인이 필요한 요소: … — 제목에 없을 뿐, 연구에 없다는
뜻은 아닙니다. 원문에서 확인하세요." 의 뒷문장은 불필요. (5) "제목에 있음/없음만 보여주는 비교가 의미가 있나."

**한 것 (계산 로직 변경 없음, 시험 240 → 241 통과):**

1. **비교함** — 빈 상자는 "제목에서 확인할 수 있는 연구요소를 나란히 비교합니다." 한 줄(권장 건수는 제목 옆 `권장 2~3개` 가 이미 말한다).
   점선 상자 안쪽 여백 1rem → 1.35rem/1.2rem, 제목과의 간격 .55rem. 담긴 카드는 항목마다 위아래 .5rem 여백 + 항목 사이 1px 구분선, 상자 안쪽 여백
   1.15rem/1.3rem.
2. **선택한 과제 비교 = 과제(열) × [레코드 사실 + 연구요소](행) 표.** 요소가 없어도 **기관 · 선정연도 · 사업** 세 줄을 과제별로 나란히 놓는다
   (`FACT_ROWS`, D1 공개 필드만, 결측은 `—`). 요소가 있으면 그 아래에 요소 행(`제목에 있음/없음`)이 굵은 경계선(`tr.grp`) 뒤에 붙는다.
   요소가 없을 때 안내는 "**요소 넣기**에 낱말을 적으면 제목에 그 낱말이 있는지도 함께 비교합니다." 한 줄.
3. **안내 축약** — 표 아래는 "확인이 필요한 요소: 공정 · 최적화" 만. "제목에 없을 뿐 … 원문에서 확인하세요" 는 그 줄의 `title`(마우스 올림) 로 옮겼다
   (`NEEDS_REVIEW_HINT`). 전부 있음일 때의 "제목에 낱말이 있다는 사실이지 …" 상시 안내는 삭제. 메모의 "아직 확인하지 못한 사항" 절은 그대로다.

**(5) 에 대한 답:** D1 에는 초록·요약이 없어 자동으로 낼 수 있는 근거는 "제목에 그 낱말이 있는가" 하나뿐이다(v2 §9). 그 자체는 약한 근거이고,
이 표의 쓸모는 **담은 2~3건 중 어느 것을 원문에서 먼저 열어 볼지** 고르는 데 있다. 이번에 레코드 사실 행을 앞에 두어 요소 없이도 비교가 되게 했다.
그래도 가치가 낮다고 판단되면 절을 접힘으로 내리거나 비교함에 합치는 것은 사용자 결정으로 남긴다.

**의미 보존 확인:** 칸 라벨은 여전히 `제목에 있음` / `제목에 없음` 이라 "연구에 없음" 을 주장하지 않는다(v2 절대 규칙 "표현 발견 ≠ 연구내용 사실").
뒷문장 삭제는 명세 §9 의 상시 안내 요구를 완화한 **명세 이탈**이며, 설명은 툴팁·메모에 남는다. `FORBIDDEN_PHRASES` 시험 통과.
시험: `test_comparison_table_labels_do_not_claim_absence` 갱신, `test_comparison_without_elements_shows_record_facts_table` 추가.

## D-033. 사용자 검토 7차 — 선택한 과제 비교를 레코드 사실·데이터 맥락 표로, 요소 비교는 접힘으로, 메모는 압축판 (2026-09-10)

**요청(사용자):** (1) "선택한 과제 비교 란을 개선할 필요. 데이터 링크나 부가 정보(데이터 크기 등)를 넣자. 제목에 요소가 있는지 없는지는 별로 중요하지
않으니 연구자가 실제로 필요한 정보를." (2) "메모 미리보기에는 보관함에 넣은 것(데이터 링크), 검색 결과, 메모만 있으면 된다. 필요 없는 정보가 너무 많다."

**데이터 확인:** D1 원본 컬럼은 `사업년도·선정년도·대사업명·중사업명·소사업명·세부사업명·과제명·연구책임자명·연구자번호·주관기관명·보안과제여부` 11개.
과제별 상세 URL·연구비·기간·초록·과제번호는 **없다**. 링크는 데이터셋 페이지 하나이고 개별 URL 조합은 금지(v2 §11). 연구책임자명·연구자번호는 개인식별 컬럼.
"데이터 크기" 는 과제별로 존재하지 않는다 → 대신 **수록 데이터 안의 맥락(레코드 수)** 을 준다.

**한 것 (검색·순위 로직 무변경, 시험 241 → 244 통과):**

1. **선택한 과제 비교 = 과제(열) × 행:** 기관 · 선정연도 · **사업 계층 4단계**(대 › 중 › 소 › 세부, 정제 데이터에서 조회) · **같은 사업의 수록 레코드**
   (가장 세부 단계 기준, 선정연도별 수 병기) · **같은 기관의 수록 레코드**(연도별 병기) · **찾은 검색**(관점 · 실제 검색문 · 순위) · **원본 위치**

## D-034. `이 범위로 다시 탐색` 진행 표시 위치 통일 · 콜드 스타트 실측 (2026-09-10)

**요청(사용자):** "선정년도·대사업명을 넣고 재검색을 돌리면 검색 중 표시가 오른쪽에 치우쳐 나온다. UI 일관성을 확인해 달라." 그리고 "서버 실행 뒤 예열 시간이 어느 정도인가."

**원인:** `render_filter_panel` 의 `이 범위로 다시 탐색` 버튼이 **접힘(`검색 범위`) 안, 오른쪽 열에서** 바로 `execute()` 를 불렀다. `execute()` 는 스켈레톤과
`st.status("검색 중 …")` 를 *호출 위치* 에 그리므로 진행 표시가 오른쪽 접힘 안에 나타났다. `탐색` 버튼은 접힘 두 개 아래에서 실행하므로 표시 위치가 달랐다.

**한 것:** 버튼은 `session_state["_refilter"]` 표시만 남기고, 실행은 `run_refilter()` 가 **관점 행(UX-W)·검색문 행(UX-L) 아래, `탐색` 과 같은 자리**에서 한다.
같은 스크립트 실행 안에서 처리되므로 클릭 → 검색 지연은 없다. 시험 `test_filter_change_...`(btn_refilter) 그대로 통과. 화면 시험 29개, 전체 244개 통과.

**콜드 스타트 실측 (이 노트북, 백그라운드에 Streamlit 1개·크롬 1개 떠 있는 상태, 헤드리스 크롬 CDP 조작):**

| 단계 | 시간 | 내용 |
|---|---|---|
| 프로세스 실행 → HTTP 응답 | 1.4 s | Streamlit 자체 기동 |
| 첫 접속 → 검색칸 표시 | **22.9 s** | `load_engine` — torch·BGE-M3 임베더·인덱스·정제 데이터 적재 (`st.cache_resource`, 첫 세션에서만) |
| 첫 검색 | 3.9 s | 재정렬기 첫 적재 포함 |
| warm 검색 3회 | 4.3 · 4.8 · 4.9 s | handoff §3.1 의 2.1~6.8 s 범위 안 |

즉 **서버를 켠 뒤 누군가 첫 페이지를 열어야 모델이 올라간다.** 시연 전 리허설: 서버 실행 → 브라우저로 한 번 접속(약 25 초) → 검색 한 번(재정렬기 적재) 까지 마쳐 두면
이후 검색은 4~5 초. 시작 시 자동 예열(첫 세션 전 적재)은 넣지 않았다 — `st.cache_resource` 구조상 첫 세션이 적재를 맡고, 시연 절차로 해결 가능해서다. 필요하면
`main()` 앞에서 `get_engine()` + 더미 검색 1회를 부르는 예열을 추가할 수 있다.

  `ModuleNotFoundError: No module named 'torchvision'` **경고 트레이스백 505줄**을 남기고 있었다(warning 레벨, 별도 스레드라 재실행 지연은 없음).

## D-038. 한 페이지 골격 — 첫 화면/결과 화면 전환 제거, 결과는 검색 상자 아래에 (2026-09-14)

**요청(사용자):** 검색 뒤 첫 화면의 스켈레톤이 뜨다가 **전혀 다른 골격의 결과 화면**으로 바뀌는 것이 어색하다 — 1페이지를 재사용할 수 없나. 의견을 먼저 듣고 승인.

**원인:** 두 화면이 서로 다른 골격이었다(머리: 마크·제목 vs 브랜드 버튼·연구주제 한 줄 / 검색 상자: 검색 방식 4탭·범위 한 줄 vs 관점 행·접힘 2개 / 오른쪽: 수록 데이터 구성 vs 비교함 /
아래: 수치 띠·바닥글 vs 결과·비교·메모). 스켈레톤은 검색 상자 안에 그려지고 `st.rerun()` 이 결과 골격을 통째로 새로 그렸다.

**결정 (D-031 "검색 후 결과 화면으로 전환" 을 대체):**
1. **골격 하나.** 띠 → 머리말 → `[검색 상자 70% | 오른쪽 30%]` → (왼쪽 열 안: 최근 탐색 · 결과) → 선택한 과제 비교 → 탐색 메모 → 데이터 및 검색 정보 → 수치 띠 → 바닥글 → 화면 모드.
   검색 전에는 결과·비교·메모 절만 없고 나머지는 같은 자리다. 상단바·브랜드 버튼·`이전 결과로 돌아가기`·`view_home` 상태 제거.
2. **검색 상자는 같은 위젯·같은 키.** 검색 방식 4탭은 검색 뒤에도 남는다. `연구주제 한 문장` 탭은 첫 검색 뒤 `[탐색 관점 | 현재 검색문 | 탐색]` 행(+ `탐색 요소 조정` 접힘)이 되고,
   어느 탭에서 검색하든 결과가 나오면 이 탭으로 돌아온다(`mode_seed`). 검색 범위 한 줄은 검색 전후 공통이며 범위가 결과와 다르면 `이 범위로 다시 탐색` 이 그 줄 아래 나타난다
   (`검색 범위` 접힘 제거, `render_filter_panel` 삭제). `연구분야로 찾기` 의 넣기 단추는 검색 전 `연구주제로 넣기`, 검색 뒤 `검색문에 넣기`.
3. **스켈레톤·진행 표시는 결과 자리에.** 검색 상자 아래 `rc_results` 컨테이너를 상자 내용보다 **먼저 만들고**(`_RESULTS_SLOT` 전역, 매 실행 갱신) `execute()` 가 거기 그린다.
   로딩과 결과가 같은 자리에서 교체된다. `st.rerun()` 은 유지(관점 행·오른쪽 패널을 새 실행에 맞추는 데 필요).
4. **오른쪽 30%** = 검색 전 `수록 데이터 구성`, 검색 뒤 `비교함 + 표시 중인 N건의 구성`(`rc_right` sticky). UX-L 은 늘 수록 데이터 구성. 최근 탐색 칩을 누르면 오른쪽 패널이
   칩보다 먼저 그려진 상태라 `render_history` 가 `st.rerun()` 으로 같은 실행에 맞춘다.
5. **연구주제 변경 경로** = `요소별 탐색` 탭(연구주제 칸) 또는 `연구 요약 붙여넣기` 탭. `연구주제 한 문장` 탭의 입력은 검색 뒤 `현재 검색문`(관점 검색문 직접 수정, `user_edited`)이다 —
   검색문과 연구주제를 같은 칸에 섞지 않는다(D-024 의 작업공간 규칙 유지).
6. 데이터 및 검색 정보: 검색 전에는 `관련 연구분야` 접힘을 싣지 않는다(`연구분야로 찾기` 탭과 같은 기능). 수치 띠·바닥글은 항상 페이지 끝.

**시험:** `test_app.py` 40 유지 — `test_home_button_returns_to_landing_and_back_keeps_results` → `test_one_page_keeps_search_box_and_appends_results`(띠·머리말·검색 상자 유지, 관점 행·범위 줄,
