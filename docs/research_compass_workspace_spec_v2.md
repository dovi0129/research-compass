# Research Compass 연구탐색 작업공간 구현 명세

> 문서 버전: 2.0  
> 문서 성격: 기존 검색·감사 구현을 보존하는 제품 흐름 개정 및 추가 구현 계약  
> 대상: 구현 워커 에이전트, 통합 담당자, 사용자 평가 담당자  
> 기본 경로: 로컬 검색 → 탐색 관점 조절 → 과제 선택 → 제목 근거 비교 → 탐색 검토 메모  
> 기본 비활성화: 생성형 LLM, NPU·외부 추론, 전역 관련도 임계값에 의존하는 미검증 분석  
> 적용 단위: 달력 일정이 아니라 작업 의존성·산출물·검증 조건

---

## 0. 워커가 먼저 읽을 실행 요약

**새로운 검색 시스템을 처음부터 만들지 않는다.** 이미 있는 데이터 감사, 전처리, BGE-M3 임베딩, FAISS 검색, 재정렬기, 평가 도구를 재사용한다. 이번 변경의 중심은 검색 모델 추가가 아니라 사용자의 탐색 작업을 완성하는 것이다.

이번 기본 구현의 완료 흐름은 다음과 같다.

```text
사용자가 연구주제 입력
  → 기존 검색 엔진으로 가까운 과제 확인
  → 필요할 때 탐색 관점과 실제 검색문 조절
  → 참고할 과제를 비교함에 담기
  → 제목에서 확인한 표현과 아직 확인하지 못한 사항을 구분
  → 근거·확인 질문·다음 검색문이 포함된 탐색 메모 내보내기
```

실행 원칙:

1. 현재 저장소와 변경 이력을 확인한다. 기존 작업을 초기화하거나 모델·CUDA 환경을 재설치하지 않는다.
2. 진행 중인 A/E 검색 평가를 마무리할 수 있게 보존하되, 이 평가 때문에 검색 목록·비교함 UI의 구현을 대기시키지 않는다.
3. 기본 구현은 **사용자 입력·선택 + 기존 검색 + 원문 문자열 근거 + 템플릿**만으로 완성한다.
4. `tau` 확정, D2 기준기간 해소, 전체 분류코드 모집단 복원을 새 사용자 흐름의 선행 조건으로 두지 않는다.
5. 위 조건이 필요한 원래 통계·후보 기능의 검증 게이트는 그대로 유지한다. 게이트를 무력화해서 기능을 켜는 것은 금지한다.
6. 제목 미언급을 실제 연구의 부재·미해결 문제·신규성으로 바꾸지 않는다.
7. LLM 자동 질의 분해, 상세 원문 연결, NPU 가속은 별도 승인 대상이다. 이 문서가 해당 확장의 실행 승인을 의미하지 않는다.
8. 기능 구현, 실제 모델 실행, 사람 검토, 사용자 효용 검증을 별도로 보고한다.

**첫 산출물:** 기존 `reports/handoff.md` 또는 동등한 보고서에 현재 상태와 본 문서의 변경 대응표를 추가한다. 이미 검증된 감사를 문서 형식 때문에 처음부터 반복하지 않는다.

## 1. 근거, 적용 범위, 기존 명세와의 관계

### 1.1 이 문서의 근거

- **[S1] 제출 사업계획서:** `아이디어 기획 사업 계획서.hwpx`. 유사 과제, 관련 분야, 연구지원 추세, 연구기회 후보 및 근거 제공이 제출안의 범위다.
- **[S2] 기존 구현 명세:** `research_compass_implementation_spec.md`, 버전 1.0. 데이터·출처·검색·통계·판단 보류·운영 안전의 기본 계약이다.
- **[R1] 사용자가 전달한 워커 보고:** 데이터 감사, 분류체계 대조, 서버 bootstrap, G2-B1/B2/B3 평가와 미완료 사항.
- **[DESIGN] 이번 설계 결정:** 검색 모델 경쟁보다 탐색 관점 조절, 사용자 선택, 근거 비교, 후속 확인을 우선한다는 대화의 결론.

이 문서 작성 시 [S1]과 [S2]는 전체 내용을 대조했다. **최신 저장소 코드, 실제 CSV, 라벨 파일, 커밋, 성능 로그를 직접 실행·감사한 것은 아니다.** [R1]의 수치는 인계 정보이며 워커가 현 저장소의 산출물과 대조해야 한다. 이 문서의 설정값과 완료 기준은 설계 결정이지 측정 결과가 아니다.

### 1.2 우선순위

- 제출안의 원문과 실제 데이터의 사실은 이 문서로 변경하지 않는다.
- 본 문서는 아래 변경표에 명시한 **제품 범위·작업 순서·추가 인터페이스**를 개정한다.
- [S2]의 원본 보존, 개인정보 제외, 출처 추적, 미검증 통계 제한, 로컬 실행 원칙은 유지한다.
- 저장소에 본 문서보다 구체적인 승인된 개정안이 있으면 먼저 대조한다. 모순은 `docs/decisions.md`에 기록하고 영향받는 부분만 보류한다.
- 과거 의사결정 기록과 평가 결과를 삭제하거나 덮어써서 처음부터 이 설계였던 것처럼 만들지 않는다.
- 기능상의 선택은 승인된 명세를 따르고, 실제 기능 가용성은 원자료·실행 결과·manifest가 정한다. 검증되지 않은 사실은 명세 문장으로 대체할 수 없다.

## 2. 인계받은 상태와 재개 시 확인할 사항

### 2.1 재사용할 자산

[R1]에 따르면 다음이 존재한다. 정확한 경로와 실제 상태를 확인하여 재사용한다.

| 자산 | 인계받은 상태 | 재개 시 확인 |
|---|---|---|
| 원본·정제 데이터 | D1 원본 11,788행, 보안 표시 5행 제외 후 11,783건 보고 | manifest·제외 사유·원본 해시 |
| D2 | 분야 레코드 851건 보고 | 현재 파일·기간 경고·분류 대조 수준 |
| 검색 기반 | BGE-M3, FAISS/NumPy, 문자 n-gram TF-IDF | 실제 모델 revision·인덱스 호환성 |
| 재정렬 | BGE-Reranker-V2-M3 CPU 경로와 평가 진행 | 실제 설정·후보 수·채택 상태 |
| G2-B2 | 해당 하이브리드 구성의 채택 실패, 기본 비활성화 보고 | 결정 기록과 실행 기본값 일치 |
| G2-B1 | 상대 점수 margin 후보만 있고 `tau` 미확정 | 임계값을 확정으로 쓰는 코드가 없는지 |
| 평가·테스트 | Sonnet 라벨, 회귀 테스트, 증분 평가 도구 | 라벨 출처·미라벨·최신 커밋의 실제 테스트 결과 |
| 실행 환경 | 로컬과 연구실 서버의 준비 작업 보고 | 어느 환경에 어떤 코드·모델이 있는지 |

보고된 행 수·테스트 개수·버전 문자열을 코드 상수나 새 성공 기준으로 사용하지 않는다. 서버 코드와 로컬 코드의 동기화 상태를 먼저 확인한다. 보고 이후 해결된 문제를 다시 미해결로 만들지 않는다.

### 2.2 검색 조건 명칭

현재 보고의 다음 두 조건만 최종 기본 경로 후보로 우선 다룬다.

- **Retrieval-A:** BGE-M3 의미검색 단독.
- **Retrieval-E:** 의미검색 후보에 BGE-Reranker-V2-M3 적용. 우선 검토 후보 수는 보고에서 사용한 20개다.

후보 50개 설정, TF-IDF, 하이브리드 등은 기존 평가·비교 경로로 보존하되 자동으로 기본 경로에 추가하지 않는다. 기존 C/D/E′ 등의 정확한 정의는 저장소 조건 매트릭스를 따른다.

**E는 유력 후보이지 이 문서만으로 채택 완료가 아니다.** 미라벨을 포함한 P@5 구간, 모델 라벨 기준 점수, 일부 warm 측정으로 채택을 확정하지 않는다. 아직 기본 경로가 결정되지 않았다면 A로 작업공간 구현을 시작할 수 있다.

### 2.3 초기 병목 점검의 한계

실패 사례는 다음처럼 기록할 수 있다.

- 후보 안에 있지만 순위가 낮은 사례.
- 다른 탐색문·방식에서는 발견되지만 현재 후보에서 빠진 사례.
- 제목만으로 판단할 수 없는 사례.
- 점검한 탐색 범위에서 충분한 근거를 확보하지 못한 사례.

마지막 항목을 “원래 코퍼스에 존재하지 않는다”로 바꾸려면 별도 근거가 필요하다. 제한된 검색 실패로 데이터 전체의 부재를 증명하지 않는다.

## 3. 제품 목표와 비목표

### 3.1 제품 정의

> Research Compass는 공개 연구과제를 탐색하면서 사용자가 자신의 검색 관점을 조절하고, 확인한 근거와 미확인 사항을 정리하도록 돕는 연구탐색 작업공간이다.

주요 사용자는 연구주제가 아직 구체화되지 않은 대학원생·신진연구자 및 새로운 분야를 탐색하는 연구자다. 특정 사용자가 이 기능을 유용하게 느낀다는 것은 구현 후 평가할 가설이다.

### 3.2 사용자가 완료해야 할 작업

사용자는 다음 질문에 답할 수 있어야 한다.

1. 어떤 검색 관점에서 이 과제를 찾았는가?
2. 현재 제목에서 내 관심 요소와 관련해 실제로 확인할 수 있는 표현은 무엇인가?
3. 제목만으로 확인되지 않아 상세 자료가 필요한 사항은 무엇인가?
4. 다음에 어떤 검색이나 확인을 하면 되는가?

결과물이 반드시 긍정적인 연구기회일 필요는 없다. **현재 자료로 충분한 근거를 확보하지 못했다는 메모도 정상 결과물**이다.

### 3.3 이번 기본 범위

- 기존 검색 엔진을 호출하는 단일 로컬 웹 화면.
- 사용자가 확인·수정할 수 있는 탐색 요소와 실제 검색문.
- 관점별 독립 검색, 과제 선택, 비교함.
- 원문 표현 발견과 사용자 검토를 구분하는 제목 근거 비교표.
- 검토할 질문·다음 검색문을 제시하는 규칙 기반 후속 작업.
- Markdown 탐색 메모와 JSON 내보내기.
- 원래 분석 기능의 가용성·제약 표시.
- 검색 품질 점검과 소규모 사용자 작업 평가.

### 3.4 구현하지 않을 것

연구공백·독창성·선정 가능성 자동 판정, 종합 기회점수, 연구방법 창작, 모든 관점의 자동 병렬 탐색, 자율 멀티에이전트 검색, 새 모델 경쟁, NPU 연동, 회원가입, 사용자 DB, 공용 공개 배포, 일괄 상세 원문 수집은 기본 범위가 아니다.

‘방법 중심’ 검색에서 나온 과제를 ‘직접 유사과제’로 재정의하여 기존 P@5를 높이지 않는다. 서비스 차별성이나 사용자 효용은 이름·UI 모양만으로 입증되지 않는다.

## 4. 데이터와 해석의 고정 경계

### 4.1 D1: 과제 제목과 메타데이터

현재 인계 기준으로 D1은 과제명·사업·기관·연도 등의 정보를 제공하며 초록·공식 과제별 분야 연결키가 없다. 구현 시 실제 데이터 스키마가 다르면 감사 결과를 우선한다.

- 제목은 원문 그대로 보존한다.
- 의미검색용 정규화 텍스트와 인용·강조용 원문을 분리한다.
- 연구자번호·연락처·신청서 개인정보는 검색·비교·메모에 넣지 않는다.
- 보안 표시 행의 기존 제외 정책을 유지한다.
- 로컬 `record_id`를 공식 과제번호로 표시하지 않는다.
- 같은 제목만으로 서로 다른 과제를 병합하지 않는다.
- 자료가 제목뿐이면 비교 결과의 `evidence_scope`는 `title_only`다.

### 4.2 D2: 분야명 탐색과 원문 통계

- 분야명 검색은 D1 과제 검색과 독립적으로 동작한다.
- 분야의 의미검색 결과를 개별 과제의 공식 분야 코드로 저장하지 않는다.
- 기준기간 충돌이 남아 있으면 원문 통계는 원래 컬럼명·충돌 안내와 함께 펼침 영역에만 표시한다.
- 기준기간 충돌을 설정값 하나로 `verified`로 바꾸지 않는다.
- 검증 전에는 선정횟수 기준 순위·색상 강조·저빈도 추천·기간 비교 차트를 만들지 않는다.
- 사용자에게 보여줄 분야는 의미검색 순위 또는 사용자가 선택한 순서다. 빈도순 추천이 아니다.
- 미등장·결측을 0건으로 바꾸지 않는다.

### 4.3 분류체계 자료

[R1]의 최신 대조는 구판 체계의 **중분류 코드 및 명칭 정합성**을 확인한 것으로 전달되었다. 소분류 6자리 코드 exact match가 완료됐다고 바꾸어 기록하지 않는다.

분류체계 버전 추정 근거, 검증한 계층, 이름 매칭 방식, 미확인 소분류 매핑을 별도로 보존한다. 구판·개정판을 섞어 모집단을 계산하지 않는다. `unobserved`는 계속 `unobserved`이며, 완전한 코드표 확보 자체도 ‘미등장=선정 0건’의 증거는 아니다.

분류표 추가 조사와 전체 모집단 복원은 이번 작업공간의 선행 조건이 아니다.

### 4.4 해석 규칙

다음 세 문장을 서로 구분한다.

- **표현 발견:** 제목 문자열에서 특정 표현을 찾았다.
- **관련성 판단:** 그 표현·제목이 사용자의 관심과 어떤 관계인지 검토했다.
- **연구내용 사실:** 실제 과제가 어떤 방법을 사용했고 무엇을 해결했는지 확인했다.

현재 제목 기반 자동 기능이 직접 확정할 수 있는 것은 주로 첫 번째다. 두 번째는 출처와 판단 주체를 표시한다. 세 번째는 제목보다 풍부한 실제 근거가 없으면 확정하지 않는다.

예를 들어 ‘강화학습을 사용하지 않는 제어’라는 제목에서 ‘강화학습’이라는 문자열을 찾았다고 해서 강화학습을 사용한 연구라고 판정해서는 안 된다.

## 5. 전체 처리 구조

```text
[기존 자산]
정제 D1 / D2 + 모델·인덱스 + manifest + capabilities
                 │
[작업공간]
원래 연구주제 + 사용자 탐색 요소
                 │
        사용자가 관점·검색문 확정
                 │
     기존 검색 service() 호출 1회
     ├─ 실제 질의·필터·엔진·점수 기록
     └─ 원문 제목·출처 반환
                 │
        사용자가 과제를 선택
                 │
   제목 표현 탐색 + 사용자 근거 검토
                 │
     비교표 + 후속 확인 질문
                 │
      탐색 메모 Markdown / JSON

[독립 보조 영역]
D2 분야명 탐색 / 범위가 명시된 레코드 구성 /
원래 추세·저빈도 후보 기능의 가용성
```

기존 UI가 있으면 그 위에 확장한다. 새 HTTP API, 프런트엔드 프레임워크, DB, 오케스트레이션 프레임워크를 만들지 않는다. UI와 CLI는 같은 검색·비교·메모 로직을 호출한다.

## 6. WFR-01 — 연구주제와 탐색 관점

### 6.1 최초 입력

첫 화면에서는 연구주제 한 문장만 받는다. 입력 직후 탐색 요소를 모두 작성하게 강요하지 않는다.

- 원래 입력: `idea_text`.
- 기본 관점: `full`.
- 기본 실행문: `effective_query = idea_text`의 검색용 공백 정리본.
- 문자열 길이·토큰 제한은 기존 검색 계약을 재사용한다.
- 첫 결과가 나온 뒤 `탐색 관점 바꾸기`를 열 수 있다.

### 6.2 사용자 탐색 요소

선택 입력은 최대 세 종류다. 일부만 입력하거나 생략할 수 있다.

| 키 | UI 이름 | 예시 역할 |
|---|---|---|
| `target_context` | 대상·맥락 | 무엇 또는 어떤 상황을 다루는가 |
| `method_approach` | 방법·접근 | 어떤 방법·관점을 참고하려는가 |
| `goal_question` | 목표·질문 | 무엇을 설명·개선·탐구하려는가 |

인문사회 주제에도 사용할 수 있게 단순 자유 텍스트로 구현한다. 특정 학문분야 분류나 필수 방법론을 강요하지 않는다.

기본 버전에서는 사용자가 직접 입력하거나 원래 문장에서 표현을 선택한다. 입력하지 않은 요소를 규칙·LLM이 임의로 보완하지 않는다.

각 요소는 `element_id`, `role`, `text`, `origin`, `confirmed`를 가진다. 사용자 직접 입력은 `origin=user_entered`, 원문 선택은 `origin=selected_from_idea`다. 원문 선택이면 정확한 문자열 범위를 함께 저장한다.

### 6.3 관점 종류와 기본 검색문

| 관점 | 표시 이름 | 기본 검색문 구성 | 입력 조건 |
|---|---|---|---|
| `full` | 전체 주제로 탐색 | 원래 연구주제 | 원래 입력이 유효 |
| `method` | 방법·접근 중심으로 탐색 | 방법·접근 + 사용자가 선택한 목표·질문 | 방법·접근 입력 필요 |
| `target_goal` | 대상·문제 중심으로 탐색 | 대상·맥락 + 목표·질문 중 입력된 항목 | 둘 중 하나 이상 필요 |

검색문 구성은 해당 요소를 순서대로 연결하는 수준으로 시작한다. 새 기술 용어·유의어·제약을 자동 추가하지 않는다.

관점별 실제 검색문은 실행 전에 항상 보이며 사용자가 수정할 수 있다. 사용자가 추가한 표현은 `query_origin=user_edited`로 기록한다. 관점 이름은 탐색 의도의 표식이지, 반환된 모든 과제가 그 의도를 충족한다는 판정이 아니다.

### 6.4 예시 — 검색 동작 설명용, 검색 성능 근거 아님

```text
원래 연구주제: 제조공정에서 강화학습을 활용한 에너지 최적화

사용자 확정 요소:
  대상·맥락 = 제조공정
  방법·접근 = 강화학습
  목표·질문 = 에너지 최적화

전체 관점: 제조공정에서 강화학습을 활용한 에너지 최적화
방법 관점: 강화학습 에너지 최적화
대상·문제 관점: 제조공정 에너지 최적화
```

방법만 보고 싶다면 사용자가 목표 요소를 해제하거나 검색문을 수정한다. 이 예시에 해당하는 실제 과제가 존재한다고 가정하지 않는다.

### 6.5 실행 제약

- 관점 선택만으로 모든 관점의 검색을 자동 실행하지 않는다.
- 사용자가 `이 검색문으로 탐색`을 눌렀을 때 선택된 관점 한 개만 실행한다.
- 관점별 결과를 RRF나 점수 평균으로 자동 통합하지 않는다.
- 질의가 달라지면 점수 분포도 다른 실행으로 취급한다. 서로 다른 질의의 원시 점수를 같은 축에서 비교해 우열을 매기지 않는다.
- 입력 부족은 이유를 안내하고 해당 관점 실행만 비활성화한다. 원래 주제 검색은 유지한다.

## 7. WFR-02 — 기존 검색 엔진 연결

### 7.1 검색 호출

기존 서비스에 `effective_query`, 필터, 결과 수, 검증된 엔진 설정을 전달한다. 관점 변경은 질의 변경이며 문서 인덱스를 재생성할 이유가 아니다.

반환값에는 다음이 있어야 한다.

- 실제 검색문과 원래 연구주제의 구분.
- 적용된 필터, 검색 대상 스냅샷, 모델·인덱스 식별자.
- 실제 사용 엔진 A/E, 재정렬 적용 여부, fallback 여부.
- 결과 순위, 의미 점수, 재정렬 점수의 구분.
- 원문 제목, 공개 메타데이터, 출처 레코드.
- 경고와 전체 처리시간.

### 7.2 재정렬과 표시 수

- 초기 작업공간 결과 수는 5개로 시작하고 10개까지 더 볼 수 있게 한다. 이는 UI 설계값이다.
- E의 재정렬 후보 수는 실제 선택된 설정에서 가져온다. 현재 우선 검토값은 20개이며 보장된 최적값이 아니다.
- 필터를 적용한 검색 대상에서 후보를 구한 뒤 재정렬한다.
- 표시 수가 재정렬된 후보 수를 넘을 때 재정렬하지 않은 결과를 같은 순위 체계인 것처럼 덧붙이지 않는다.
- 결과가 적은 경우 실제 개수와 원인을 표시한다. 빈 칸을 가짜 레코드로 채우지 않는다.
- 재정렬이 실패하면 기존 정책에 따라 A 결과로 복귀할 수 있지만, `actual_engine`과 경고를 바꾼다. 실패를 E 성공으로 기록하지 않는다.

### 7.3 `tau`와 검색 목록의 분리

검색 목록·비교함·제목 근거 검토는 순위 기반 후보로 동작한다. 전역 관련도 임계값 검증을 기다리지 않는다.

반면 다음 기능은 별도 검증 전 계속 비활성화한다.

- 코퍼스 전체에서 ‘관련 과제 총 N건’이라고 확정하는 집계.
- 관련도 기준으로 전체 모집단을 잘라 만든 연구지원 추세.
- 관련도·빈도를 결합한 연구기회 판정.

보고된 `p99`가 질의별 코퍼스 점수의 99백분위라는 정의라면 margin 기준은 상대적인 상위 구간 선택이다. 해당 상대 순위가 절대 관련성을 보장하지 않는다. 실제 함수의 p99 정의가 다르면 그 정의부터 확인한다.

UI에는 `가까운 검색 결과`라고 표시한다. 모든 후보를 ‘직접 관련 과제’로 자동 분류하지 않는다. 점수는 `의미 유사도`, `재정렬 점수`로만 표시하며 확률·정확도 백분율로 변환하지 않는다.

### 7.4 캐시·지연시간

모델·인덱스의 기존 재사용 로직을 유지한다. 사용자 질의 결과는 기본적으로 현재 세션 안에서만 재사용한다.

검색 실행의 동일성은 실제 검색문, 필터, 엔진 설정, 모델·인덱스·스냅샷 식별자, run_mode가 모두 같을 때만 인정한다. 의미가 비슷한 질의를 같은 캐시 키로 합치지 않는다.

전체 지연시간과 질의 임베딩·검색·재정렬·화면 처리 시간을 구분해 기록한다. warm 목표는 기존의 5초 이내를 사용성 목표로 유지하되 측정 환경과 분포를 함께 보고한다. 한 번의 측정만으로 일반적인 응답시간을 주장하지 않는다.

## 8. WFR-03 — 과제 선택과 작업공간 상태

### 8.1 비교함

사용자가 참고할 과제를 선택해 비교함에 담는다. 기본 최대 5개이며 이 숫자는 화면 복잡도를 줄이기 위한 설계값이다.

선택 항목마다 다음을 보존한다.

- `record_id`와 `source_snapshot_id`.
- 원문 제목·메타데이터·출처.
- 선택한 검색 실행의 `run_id`, 관점, 실제 검색문, 당시 순위.
- 여러 검색에서 선택됐으면 각 검색의 출처 이력.
- 사용자가 적은 선택 이유. 작성하지 않았으면 빈 값으로 유지.

중복 선택 키는 `(source_snapshot_id, record_id)`다. 다른 관점에서 같은 과제가 나왔다고 여러 독립 과제처럼 중복 집계하지 않는다.

### 8.2 관점·필터 변경

같은 연구주제 안에서 관점이나 필터를 바꿔도 비교함은 유지한다. 기존에 선택한 항목이 현재 필터 밖이면 `이전 검색에서 선택됨` 또는 `현재 필터 밖`을 표시한다. 자동 삭제하거나 현재 결과로 오인시키지 않는다.

검색 관점별 순위·점수는 각 실행에 종속된다. 비교함의 여러 결과를 검색 점수 하나로 다시 정렬해 종합 순위로 만들지 않는다. 기본 순서는 사용자 선택 순서다.

### 8.3 연구주제·요소 수정

- 원래 연구주제를 바꾸면 새 작업공간으로 시작하거나 현재 공간을 초기화할지 확인한다. 이전 메모를 조용히 삭제하지 않는다.
- 같은 주제의 탐색 요소를 수정하면 해당 요소의 비교 판단을 `stale`로 표시하고 다시 검토하게 한다.
- 이미 내보낸 파일은 수정하지 않는다. 새 내보내기는 새 작업공간 revision을 기록한다.
- 검색문만 바꾼 경우 이전 실행 기록은 실제 실행문 그대로 유지한다.

### 8.4 저장 정책

작업공간은 기본적으로 브라우저 세션과 앱 메모리에만 유지한다. 재접속 후 복구를 위해 DB나 자동 파일 저장을 추가하지 않는다.

`작업공간 지우기`를 제공한다. 사용자가 명시적으로 내보낼 때만 파일을 만든다. 비교함·메모·질의가 공유 전역 캐시나 서버 로그에 다른 사용자의 데이터와 섞이지 않도록 한다.

## 9. WFR-04 — 제목 근거 비교표

### 9.1 비교 단위

비교표의 기본 단위는 **사용자 탐색 요소 × 선택한 과제**다. 각 칸은 제목에서 발견한 표현, 검토 상태, 원문 위치를 가진다.

사용자 요소가 없으면 자동 분해하지 않는다. 선택한 제목을 보여주고 요소 입력을 안내한다. 요소 없이도 과제 선택 이유와 미확인 사항을 직접 적어 메모를 만들 수 있다.

### 9.2 표현 발견과 의미 판단의 구분

자동 기능의 기본 출력은 다음과 같다.

| `finding` | UI 표기 | 자동 생성 조건 |
|---|---|---|
| `expression_found` | 제목에 표현 있음 — 의미는 검토 필요 | 사용자 요소의 표현이 제목 원문에서 발견됨 |
| `needs_review` | 해당 표현 자동 미검출 — 직접 검토 필요 | 완전한 표현을 찾지 못했거나 자동 확인이 어려움 |
| `not_confirmed_in_title` | 제목에서 확인되지 않음 | 사용자가 제목을 검토한 뒤 명시적으로 선택 |

`needs_review`는 ‘연구하지 않음’, ‘무관함’, ‘차별 요소’가 아니다. 자동 검색이 유의어·다른 표기·문맥을 놓쳤을 수도 있다.

`expression_found`는 그 연구가 해당 방법을 사용했다는 의미가 아니다. 단어의 부정·비교·비판 문맥이 있을 수 있으므로 사용자가 전체 제목을 보고 판단해야 한다.

### 9.3 구현할 최소 자동 기능

1. 사용자 요소의 원문 표현이 제목에 그대로 있는지 검사한다.
2. 발견한 범위를 원문에서 강조한다.
3. 없으면 `needs_review`로 남긴다.
4. 부분 단어가 발견되더라도 복합 요소 전체가 확인됐다고 표시하지 않는다.

초기 구현은 원문 literal match만으로 가능하다. 유니코드·공백 정규화 비교를 추가할 경우 원문 위치를 정확하게 복원할 수 있어야 한다. 복원할 수 없는 매칭을 원문 인용으로 만들지 않는다.

LLM·새 의미 판별 모델·광범위한 유의어 사전은 기본 구현에 필요하지 않다. 문자열 일치를 의미 이해의 정확도로 평가하지 않는다.

### 9.4 사용자 검토

사용자는 각 칸에서 다음을 할 수 있다.

- 원문 제목 중 근거 구절 선택 또는 원문과 정확히 일치하는 구절 입력.
- 그 구절과 관심 요소의 관계를 메모.
- 제목만으로 해당 요소를 확인하지 못했다고 표시.
- 잘못된 자동 발견의 의미 연결을 거부.

검토 주체는 `user`로 기록한다. 사용자가 연결을 승인해도 실제 연구내용 전체를 검증했다고 표시하지 않는다. 사용자가 작성한 “이 과제는 X를 하지 않았다” 같은 해석은 사용자 메모로만 보존하며 시스템 확인 사실로 승격하지 않는다.

### 9.5 근거 위치 계약

각 인용은 다음을 포함한다.

```text
source_dataset_id
source_snapshot_id
record_id
field_name = title_raw
quote
start_offset
end_offset
source_text_sha256
```

offset은 원문 문자열의 **0부터 시작하는 Unicode 코드포인트 기준, 끝 위치 미포함**이다. 바이트 위치·화면 글자 폭과 혼용하지 않는다.

검증식:

```text
title_raw[start_offset:end_offset] == quote
```

원문 해시는 정규화 전 `title_raw`를 UTF-8로 인코딩한 바이트의 SHA-256으로 계산한다. 원문이 변경됐거나 인용이 일치하지 않으면 경고와 함께 그 근거를 확정 메모에서 제외한다. 원문에 있는 문자열이라는 검사와 그 문자열이 판단을 뒷받침한다는 사람 검토를 분리한다.

### 9.6 허용·금지 표현

허용 예시:

- “제목에 ‘강화학습’이라는 표현이 있다.”
- “사용자가 방법 관련 참고 후보로 선택했다.”
- “제목만으로 에너지 절감 성과를 확인할 수 없다.”
- “상세 연구목표에서 제조공정 적용 여부를 추가 확인해야 한다.”

금지 예시:

- “기존 연구는 에너지 최적화를 다루지 않았다.”
- “사용자의 주제가 기존 과제보다 독창적이다.”
- “이 조합은 연구된 적이 없다.”
- “표현 세 개가 일치하므로 동일 연구다.”

### 9.7 예시 — 합성 테스트 제목

아래 제목은 동작 검증용 fixture이며 실제 과제라고 제시하지 않는다.

```text
사용자 요소: 강화학습 / 제조공정 / 에너지 최적화
테스트 제목: 강화학습을 이용한 추천시스템 분석

강화학습 → 표현 발견, 정확한 구절 강조, 의미 검토 전
제조공정 → 표현 자동 미검출, 직접 검토 필요
에너지 최적화 → 표현 자동 미검출, 직접 검토 필요
```

제목이 `강화학습을 사용하지 않는 추천시스템 분석`으로 바뀌어도 자동 결과는 표현 발견일 수 있다. 이때도 ‘강화학습 사용 확인’ 문장은 생성되면 안 된다.

## 10. WFR-05 — 다음 탐색과 확인 작업

### 10.1 기능 정의

화면 이름은 **다음 탐색·확인**이다. 학술적 연구기회 또는 저빈도 분야 판정과 구분한다.

사용자가 입력·확인한 요소, 선택한 과제, 비교표 상태로부터 다음 작업을 제안한다. 기본 출력은 최대 3개이며 정해진 규칙 순서로 보여준다. 기회점수나 성공 가능성 순위가 아니다.

### 10.2 기본 규칙

| 상황 | 제안할 작업 | 제안 근거 |
|---|---|---|
| 제목에서 요소를 확인하지 못함 | 선택 과제의 연구목표·요약에서 해당 요소를 확인 | 해당 요소와 선택 과제 |
| 방법 관점만 탐색했고 대상·목표 요소가 있음 | 대상·문제 중심 검색문 미리보기 | 사용자가 확정한 요소 |
| 대상·문제 관점만 탐색했고 방법 요소가 있음 | 방법·접근 중심 검색문 미리보기 | 사용자가 확정한 요소 |
| 사용자 판단으로 현재 결과가 충분하지 않음 | 검색문을 더 넓게/다르게 수정하도록 편집창 열기 | 사용자의 부족 표시와 실행 이력 |
| 사용자가 D2 분야명을 선택함 | 그 분야명으로 별도 탐색문을 작성·확인 | 실제 D2 레코드와 사용자 선택 |
| 확인되지 않은 항목이 없거나 제안 근거 부족 | 추가 제안 없음 | 억지로 세 개를 채우지 않음 |

새 검색은 사용자가 확인한 뒤에만 실행한다. 상세 원문 연결이 구현되지 않았다면 ‘상세 자료 확인 필요’ 작업만 만들며 자료를 이미 가져온 것처럼 쓰지 않는다.

### 10.3 생성 제한

- 사용자 입력이나 실제 선택 분야에 없는 ‘안전제약’, ‘오프라인 RL’, ‘전이학습’ 등의 주제를 임의 추천하지 않는다.
- 검색 결과가 적다는 이유로 창의적·유망하다는 배지를 붙이지 않는다.
- ‘이 제목에서 확인되지 않음’을 전체 학계의 미해결 질문으로 바꾸지 않는다.
- `next_actions`와 기존 `opportunity_candidates`는 별도 출력 필드·기능 상태로 유지한다.
- 사용자가 제안을 수정하면 수정 이력과 `user_edited`를 기록한다.

## 11. WFR-06 — 탐색 검토 메모

### 11.1 출력 목표

지도교수 면담·팀 논의를 위해 참고할 과제와 다음 확인사항을 정리한 **짧은 탐색 메모**를 제공한다. 한 장 내외의 요약을 지향하되 모든 출처를 숨기거나 내용이 잘리게 제한하지 않는다.

기본 출력 형식:

- `research_compass_memo.md`: 사람이 읽는 요약 및 근거 부록.
- `research_compass_workspace.json`: 실행·선택·판단 근거를 보존하는 구조화 데이터.

기존 검색 CSV/JSON 출력은 유지한다. PDF/DOCX 생성, JSON 재업로드 UI, 장기 프로젝트 저장은 기본 범위가 아니다.

### 11.2 메모 구성

```markdown
# Research Compass 탐색 검토 메모

## 연구주제
원래 사용자 입력

## 탐색한 관점
관점별 실제 검색문, 필터, 실제 사용한 검색 엔진

## 참고 후보로 선택한 과제
원문 제목 / 공개 메타데이터 / 발견한 검색 관점 / 사용자 선택 이유

## 제목에서 확인한 표현과 검토 내용
원문 인용 / 표현 발견 또는 사용자 검토의 구분 / 근거 번호

## 아직 확인하지 못한 사항
제목만으로 판단할 수 없는 항목과 상세 자료 확인 질문

## 다음 탐색·확인
사용자가 확인한 다음 검색문 또는 확인 작업

## 범위와 제한
사용 데이터, 제목 기반 비교, 독립 분야 검색, 제한된 분석 기능

## 근거 부록
데이터셋·스냅샷·레코드·원문 위치·모델/실행 식별자
```

### 11.3 자동 사실·사용자 의견의 분리

- 자동 literal match는 ‘자동 발견 표현’으로 표시한다.
- 사람이 확인한 연결만 ‘사용자 검토 내용’으로 표시한다.
- 검토하지 않은 자동 제안은 확정된 내용에 포함하지 않고 미검토 영역에 둔다.
- 사용자 선택 이유와 의견은 별도 열에 표시한다. 공식 과제 설명으로 바꾸지 않는다.
- `stale` 또는 인용 검증 실패 항목은 확정 영역에서 제외하고 재검토 사유를 표시한다.
- ‘판단 보류’ 항목을 긍정적인 성과로 바꾸어 요약하지 않는다.

### 11.4 선택한 과제가 없는 경우

메모 내보내기는 허용한다. 검색문·범위·사용자 판단·다음 확인사항을 기록하고 다음과 같이 표시한다.

> 현재 탐색에서는 참고 후보를 선택하지 않았습니다. 이 결과는 해당 연구가 없다는 의미가 아닙니다.

템플릿을 채우기 위해 가짜 과제·근거·추가 연구방향을 만들지 않는다.

### 11.5 출처와 재현성

메모 안의 `[E1]` 같은 번호는 **이 메모의 근거 번호**다. 공식 과제번호로 표시하지 않는다.

각 근거는 원본 데이터 페이지, 스냅샷 식별자, 로컬 레코드 ID, 원본 행 위치로 추적 가능해야 한다. 공식 개별 상세 URL을 모르면 임의로 조합하지 않는다.

같은 작업공간 snapshot을 입력하면 실행시각 같은 명시적 메타데이터를 제외한 내용은 결정적으로 생성한다. 내보내기 전에 인용·출처·검토 상태를 검증한다. 기록된 연구주제·메모가 파일에 포함된다는 것을 다운로드 버튼 옆에 안내한다.

## 12. 보조 분석과 원래 기능의 상태 표시

### 12.1 집계 범위를 분리

다음 범위를 서로 다른 값으로 다룬다.

| `scope_kind` | 의미 | 가능한 표현 |
|---|---|---|
| `dataset_snapshot` | 다운로드한 자료의 수록 레코드 | 자료에 수록된 선정년도 구성 |
| `displayed_results` | 특정 검색 실행에서 표시한 후보 | 현재 표시된 검색 후보의 연도 구성 |
| `selected_records` | 사용자가 고른 중복 제거 레코드 | 비교함에 담은 레코드의 연도·사업 구성 |
| `calibrated_relevant_corpus` | 검증된 관련도 기준을 전체 필터 대상에 적용한 집합 | 조건이 충족될 때만 관련 레코드 집계 |

첫 세 범위의 기술통계는 전역 `tau`를 요구하지 않는다. 마지막 범위는 기존 검증이 필요하다.

`displayed_results` 집계는 표시 수가 바뀌면 바뀔 수 있다. `selected_records` 집계는 비교함이 바뀌면 바뀔 수 있다. **기존 Top-K 독립성 테스트는 `calibrated_relevant_corpus`에 계속 적용한다.** 서로 다른 범위를 한 필드로 구현해서 기존 테스트를 단순 삭제하지 않는다.

각 집계에 `scope_kind`, 대상 레코드 ID, 대상 수, 필터·검색 실행, 미상 값 수를 기록한다. 서로 다른 관점에서 같은 과제를 중복 집계하지 않는다.

### 12.2 추세 표시 금지 조건

사업 구성·수록 단위·기간 비교 가능성이 검증되지 않으면 증가율·감소율·성장성 문구를 출력하지 않는다. 비율로 정규화해도 대표성 문제가 자동으로 해결됐다고 간주하지 않는다.

관측하지 않은 기간을 임의의 0건으로 채우지 않는다. 선택 집합 내 구성을 설명할 때도 그 집합의 범위를 명시한다. 자료의 수록 구성 변화만 보고 실제 지원 정책의 증감을 설명하지 않는다.

### 12.3 D2 표시

D2 결과는 `분야명으로 더 탐색` 보조 영역에서 제공한다. 원문 통계가 제한돼도 분야명 검색 자체는 계속 사용할 수 있다.

분야 카드를 선택하면 사용자가 새 검색문을 확인할 수 있다. 이것은 분야 탐색이지 D1 과제에 대한 공식 분야 배정이 아니다.

### 12.4 기능 상태

최소 다음 기능은 독립 상태를 가진다.

```text
ranked_project_search
perspective_search
comparison_workspace
title_evidence_review
exploration_memo
field_name_search
field_count_display
scoped_distribution
calibrated_relevant_corpus
comparable_trend
project_field_join
opportunity_candidates
```

기존 `capabilities.json`이 다른 키를 쓰면 호환 매핑을 추가한다. 이름만 바꾸어 미검증 기능이 활성화되지 않게 한다. 상태는 `available`, `limited`, `unavailable`, `unverified` 또는 저장소의 동등한 체계를 사용하며 근거와 제한을 포함한다.

### 13.2 초기 사용자 부담

첫 검색에는 연구주제만 필요하다. 요소 입력·비교함·메모는 필요할 때 순차적으로 노출한다. 모든 항목을 채우기 전에는 검색할 수 없는 양식을 만들지 않는다.

점수·manifest·감사 세부는 펼침 영역으로 둔다. 다만 제목 기반 비교, 미검토 상태, 기간 충돌처럼 결과 해석에 직접 영향을 주는 경고는 해당 결과 가까이에 표시한다.

### 13.3 상태·실패 처리

다음 상태를 정상적으로 처리한다.

- 데이터·모델 준비 안 됨: 가짜 결과 대신 준비 절차 안내.
- 검색 중: 실제 처리 중인 검색문 표시.
- 결과는 있으나 직접 관련성 미확정: 가까운 후보로 표시.
- 필터 대상 없음: 필터 조정 안내.
- 사용자가 충분한 근거를 찾지 못함: 그 판단과 다음 확인 작업을 기록 가능.
- 일부 분석 제한: 검색·비교·메모는 유지.
- 재정렬 실패: 실제 fallback 경로 표시.
- 새 입력 후 이전 결과: 예전 실행임을 표시하거나 새 결과로 교체 전까지 분리.

초기 구현은 동기 호출로 가능하다. 비동기를 추가했다면 응답 `run_id`와 현재 요청이 다를 때 이전 응답으로 화면을 덮어쓰지 않는다.

### 13.4 모드 구분

`local_live`, `saved_replay`, `test_fixture`를 기존 명세대로 구분한다. 테스트 제목·해시 임베더·저장된 결과를 실제 모델 라이브 결과로 표시하지 않는다.

새로운 임의 질의를 처리하지 못하는 재생 모드에서 검색이 수행된 것처럼 결과를 반환하지 않는다. 실제 데모에서 실패하면 실패 상태 또는 명시적인 녹화·재생 자료로 전환한다.

## 14. 최소 내부 데이터 계약

아래는 구현할 논리 계약이다. 현재 저장소에 존재하는 클래스·함수 이름이라는 뜻은 아니다. 기존 타입에 필드를 추가하거나 얇은 어댑터를 두고, 동등한 계약을 유지한다.

### 14.1 `ExplorationElement`

```text
element_id: str
role: target_context | method_approach | goal_question
text: str
origin: user_entered | selected_from_idea | model_proposed
confirmed: bool
idea_span: {start: int, end: int, quote: str} | null

```

`model_proposed`는 선택 확장 대비 상태일 뿐 기본 구현에서 생성하지 않는다. 원래 아이디어에 없던 사용자 입력은 `selected_from_idea`로 위장하지 않는다.

### 14.2 `SearchRun`

```text
run_id: str

idea_revision: int
perspective: full | method | target_goal
original_query: str

used_element_ids: list[str]
filters: object
requested_engine: str
actual_engine: str
engine_config_id: str
model_manifest_ids: list[str]
index_manifest_id: str
source_snapshot_ids: list[str]
results: list[기존 ProjectResult]
warnings: list[기존 Warning 또는 동등 타입]
latency_ms: object
run_mode: local_live | saved_replay | test_fixture
```

### 14.3 `SelectedProject`


점수는 `origin_runs`의 실제 SearchRun에서 조회한다. 여러 질의의 점수 평균을 선택 항목의 대표 관련도로 만들지 않는다.

### 14.4 `EvidenceObservation`

```text
observation_id: str
record_id: str
source_snapshot_id: str
element_id: str
element_revision: int
```

검증 규칙:

- `expression_found`에는 유효한 원문 인용이 최소 하나 있어야 한다.
- 자동 매칭은 `review_status=unreviewed`로 시작한다.
- `not_confirmed_in_title`는 사용자 검토로만 생성한다. 부재의 인용문을 만들지 않는다.
- `model_proposal`은 자동 `confirmed`가 될 수 없다.
- 사용자 요소의 revision이나 원문 해시가 달라지면 이전 확인을 재사용하지 않는다.
- 문자열 근거 검증과 의미 관계의 사용자 확인은 별개다.

### 14.5 `NextAction`


키·토큰·개인식별 컬럼·민감한 로컬 경로는 포함하지 않는다. 실제 실행·내보내기 시각은 필요하면 런타임에서 기록하되 명세의 예시 시각으로 채우지 않는다.

## 17. 평가 계약

### 17.1 평가 목적을 분리

| 평가 | 확인할 것 | 다른 평가로 대체할 수 없는 것 |
|---|---|---|
| 검색 엔진 평가 | A/E에서 목적에 맞는 후보가 상위에 오는가 | UI가 편리하다는 증거가 아님 |
| 근거 무결성 테스트 | 인용·출처·상태가 올바른가 | 연구 관련성 자체를 보장하지 않음 |
| 사용자 근거 검토 | 제목이 선택 이유를 지지하는가 | 상세 연구내용의 진위를 보장하지 않음 |
| 작업공간 사용성 평가 | 선택·비교·미확인 정리에 실제 도움이 되는가 | 국가 전체·모든 분야 일반 성능 주장이 아님 |

### 17.2 진행 중인 A/E 평가 마무리

1. 현 저장소에서 미라벨·키 누락·중복·충돌 수를 다시 확인한다. 과거 보고의 미라벨 8건을 현재 상태라고 가정하지 않는다.
2. A/E가 같은 질의·필터·스냅샷·평가 기준으로 비교되는지 확인한다.
3. 라벨 방식과 출처를 분리한다. 기존 Sonnet 라벨은 `label_source=llm`이다.
4. 미라벨 또는 `U`가 남으면 확정값 대신 구간·미확정 상태로 보고한다.
5. 최종 기본 설정을 결정하기 전 평가 기준과 latency 기준을 기록한다. 결과를 본 뒤 유리한 기준으로 바꾸지 않는다.
6. 검증되지 않으면 A를 기본으로 유지하고 E를 선택 실험 상태로 둔다. 이 때문에 작업공간 구현을 멈추지 않는다.

A/E 선택 기준에 보편적인 P@5 합격 숫자를 이 문서에서 새로 강제하지 않는다. 기존에 합의한 게이트가 있으면 유지하고, 기준이 없다면 비교 전 개발 평가 기준을 먼저 기록한다. 개선이 없으면 채택하지 않는 결과도 정상이다.

### 17.3 라벨 출처와 평가 단위

- 같은 모델의 병렬 에이전트 여러 개를 사람 평가자 여러 명으로 표시하지 않는다.
- 한 질의를 한 에이전트가 평가했다면 다수 평가자 합의가 있었다고 쓰지 않는다.
- `human`, `llm`, `adjudicated` 등을 구분하고, 모델·프롬프트 버전 또는 익명 사람 평가자 ID를 남긴다.
- 인간 검토 수치는 별도로 보고한다. 사람 라벨과 LLM 라벨을 조용히 섞어 하나의 정확도로 만들지 않는다.
- 제목 근거가 부족하면 `U`를 사용한다. 엄격 관련과 일부 관련을 구분한다.
- 원래 전체 주제의 라벨을 방법 중심 질의에 재사용하지 않는다. 평가 단위에 `perspective`와 `effective_query`가 포함되어야 한다.

### 17.4 개발·검증 분리

이미 결과를 보고 검색 구성을 선택한 test는 개발 의사결정에 사용된 평가로 표시한다. 기록을 삭제하지 말고 `used_for_selection`을 남긴다.

최종 설정을 고정한 뒤 새로운 질의를 소규모로 확인한다. 초기 작업량 목표는 새로운 질의 5개 이상이며 통계적 충분성을 의미하지 않는다. 무조건 채워야 하는 성능 숫자나 성공 사례 수는 두지 않는다.

새 관점 기능은 최소 두 개의 실제 사용자 질의에서 전체·방법·대상 관점을 따로 검토한다. 관련성 기준은 관점의 의도를 반영하되 전체 질의 평가를 사후적으로 완화하지 않는다.

### 17.5 증분 평가 키 무결성

기존에 보고된 증분 키 덮어쓰기 문제를 회귀 점검한다.

- 기존 라벨과 pool key는 덮어쓰지 않고 버전·해시를 보존한다.
- 같은 `(query_id, item_id)`가 다른 레코드나 스냅샷을 가리키면 실패 처리한다. `keep=first`로 충돌을 숨기지 않는다.
- `item_id`의 전역 유일성이 보장되지 않으면 완료 여부를 `item_id` 하나로 판정하지 않는다.
- 기존 라벨이 새 증분 실행 후 사라지지 않아야 한다.
- 평가자에게는 필요한 질의·관점·원문만 제공하고 엔진·순위·점수는 가린다.
- 이 보강은 기존 데이터를 안전하게 유지하기 위한 작업이다. 새 라벨링 플랫폼을 만들지 않는다.

### 17.6 사용자 작업 비교

사용성 조건 이름은 검색 조건 A/E와 혼동되지 않도록 다음처럼 사용한다.

- **UX-L:** 기존 검색 목록. 원문·출처 열람, 검색문 수정, 자유 메모 가능.
- **UX-W:** 같은 검색 엔진·원자료에 관점 조절, 비교함, 근거 비교표, 탐색 메모를 추가.

두 조건에 같은 정보 접근권을 준다. UX-W에만 상세 원문이나 더 좋은 모델을 제공하면서 UI 효과라고 주장하지 않는다. UX-L도 사용자가 검색문을 수정할 수 있게 하여 비현실적으로 약한 비교 대상으로 만들지 않는다.

작업 지시:

> 관심 연구주제에 대해 참고할 과제를 고르고, 선택 이유와 아직 확인하지 못한 사항, 다음 확인 행동을 정리하세요. 현재 자료로 충분한 후보를 찾지 못하면 그 이유를 남겨도 됩니다.

소규모 파일럿은 실제 사용자 최소 3명을 초기 목표로 삼는다. 이는 사용성 탐색 규모다. 팀원만 참여했다면 개발자 친숙성 편향을 명시한다. 사용자를 확보하지 못하면 설문·기록 양식만 준비하고 사용자 평가를 수행했다고 보고하지 않는다.

서로 비슷한 난이도의 다른 주제를 사용하고 조건 순서를 번갈아 배치한다. 같은 주제를 연속으로 재사용했다면 학습효과 한계를 적는다. 모든 사용자에게 유리한 성공 예제만 주지 않는다.

### 17.7 측정할 항목

| 항목 | 기록 방법 |
|---|---|
| 작업 완료 여부 | 메모 작성 또는 근거 부족·다음 확인까지 설명했는지 |
| 근거 있는 선택 | 선택 이유가 제목·제공 메타데이터로 지지되는지 사람 검토 |
| 미확인 사항 인식 | 제목 미언급을 연구 부재로 오해하지 않는지 |
| 잘못된 확정 주장 | 시스템 생성과 사용자 작성의 근거 초과 주장을 구분해 집계 |
| 소요시간 | 시작·종료, 중단·timeout도 포함 |
| 실제 활용성 | 메모를 다시 쓰거나 면담에 가져가는 데 무엇이 부족한지 |
| 부담 | 관점 입력·비교표 작성이 불필요하게 일을 늘렸는지 |

선택 0건인 작업은 근거 있는 선택 비율을 100%로 계산하지 않고 분모 없음으로 표시한다. 작업시간이 줄었어도 근거 없는 판단이 늘면 성공으로 결론내리지 않는다.

개선이 관측되지 않으면 LLM·NPU를 추가하기 전에 흐름을 단순화하거나 실제 상세 근거가 부족한지 검토한다. 결과가 불확실하면 “유용성 미확정”으로 남긴다.

## 18. 선택 확장 — 별도 승인 후에만 실행

### 18.1 LLM 질의 구조화

허용 가능한 후속 역할:

- 원래 사용자 문장에서 탐색 요소를 추출해 제안.
- 추출 근거 구절과 수정 가능한 요소를 보여주기.
- 사용자가 확인한 요소로 검색문 초안을 제안.

제약:

- 입력에 없는 요소를 추출 결과처럼 만들지 않는다.
- 사용자 확인 전에는 검색 실행·검색문 교체·자동 추가 탐색을 하지 않는다.
- 모델 제안은 `model_proposed` 상태다.
- 실패하면 수동 입력 경로를 그대로 제공한다.
- 기본 검색 엔진과 결과 집계는 LLM에 의존하지 않는다.

### 18.2 LLM 근거 추출 보조

선택된 제목 안에서 인용 구절과 관계 후보를 제안할 수 있다. 인용 검증에 통과해도 자동 확인 사실로 승격하지 않는다. 사용자가 전체 제목을 검토해야 한다.

LLM 사용으로 검색의 직접 품질이 높아졌다고 주장하지 않는다. 질의 구조화나 검토 부담을 개선했는지 별도로 평가한다. 이 확장은 기존 명세의 단순 요약 역할보다 넓으므로 승인·변경 이력을 남긴다.

### 18.3 상세 근거 연결

KRM 등 공식 상세 자료를 후속 근거원으로 검토할 수 있으나, 이번 기본 구현에서 자동 수집하거나 D1과 정확히 연결됐다고 가정하지 않는다.

확장 시 필요한 최소 계약:

- 상세 자료의 URL·제공기관·이용 조건·원문 위치 보존.
- D1 과제와의 연결 상태를 `candidate`, `verified`, `rejected`로 구분.
- 제목 일치만으로 연결 확정하지 않기. 기관·기간·사업 등 확보 가능한 식별 근거 대조.
- 모호한 연결은 보류하며 다른 과제의 상세 내용을 합치지 않기.
- 상세 원문에서 확인한 주장과 제목에서 확인한 표현을 서로 다른 evidence scope로 표시.
- 일부 선택 과제의 확인된 연결부터 검증하고 전수 수집을 선행하지 않기.

### 18.4 인프라 확장

NPU·외부 API·클라우드 배포는 이 문서의 필수 산출물이 아니다. 운영 자원·비용·비밀정보·외부 전송이 추가되면 사용자 승인과 별도 실행 명세가 필요하다. 로컬 기본 경로를 없애지 않는다.

## 19. 구현 순서와 종료 조건

### W0 — 현 상태·변경 대응 확인

**작업:** 최신 저장소·manifest·capabilities·평가 상태·실행 경로를 확인한다. 기존 결정 기록을 읽고 본 명세의 변경표와 대조한다.

**산출물:** 기존 handoff에 변경 대응표와 실제 실행 경로 추가.

**완료:** 어떤 자산을 재사용하고 어떤 부분만 추가할지 명확하다. 최신 코드와 모델의 위치가 확인된다.

### W1 — 기존 검색을 화면에서 연결

**작업:** A 또는 이미 검증된 기본 엔진으로 입력→검색→원문·출처 표시. 사용자 관점·비교 기능이 없어도 실제 검색이 가능하게 한다.

**산출물:** 로컬 실행 화면과 간단한 실데이터 smoke 결과.

**완료:** 실제 모델·자료가 준비된 환경에서 가짜 결과 없이 검색된다. 준비되지 않은 환경은 명시적 오류를 보여준다.

### W2 — 관점 조절과 비교함

**작업:** 수동 요소 입력, 실제 검색문 확인, 단일 관점 실행, 과제 선택·제거, 실행 출처·상태 보존.

**산출물:** WFR-01~03.

**완료:** 사용자가 검색 관점을 바꾸고 여러 검색에서 얻은 과제를 원래 출처와 함께 비교함에 담을 수 있다.

### W3 — 근거 비교와 메모

**작업:** literal match, 사용자 인용 검토, 미확인 상태, 다음 확인 작업, Markdown/JSON 내보내기.

**산출물:** WFR-04~06과 근거·내보내기 테스트.

**완료:** 선택 과제의 표현·사용자 의견·미확인 사항을 섞지 않은 메모가 생성된다. 선택이 없는 실패 사례도 처리된다.

### W4 — 검색 평가 마무리와 기본 경로 고정

**작업:** A/E 미완료 라벨·실행 조건·실제 사람 검토를 확인하고 기본 엔진을 결정한다.

**산출물:** 기존 검색 평가 보고서 갱신, 선택 근거 및 지연시간 기록.

**완료:** 기본 경로와 근거가 명확하다. E가 미검증 또는 불리하면 A 유지도 완료 결과다.

W4는 W1~W3과 병행할 수 있다. UI 작업이 E 채택을 기다릴 필요는 없다.

### W5 — 사용자 작업 평가

**작업:** UX-L과 UX-W의 소규모 작업 비교. 원문 근거·오해·작업 부담을 확인한다.

**산출물:** 사용성 보고서 또는 미실시 사유와 준비된 양식.

**완료:** 구현 성공과 사용자 효용의 관측 여부가 분리되어 있다. 개선이 불명확하면 다음 조정을 기록한다.

### W6 — 제한 기능·재현 실행·인계

**작업:** D2 독립 검색, 범위가 명시된 구성 정보, 원래 FR-03/04 제한 상태를 확인하고 데모·실행 문서를 정리한다.

**산출물:** 최종 handoff, 실제 메모 예시, 제한 기능표, 실행·백업 절차.

**완료:** 기본 작업공간이 LLM/NPU 없이 실행되고, 원래 계획서 기능의 미검증 부분이 숨겨지지 않는다.

### 작업 확대를 멈출 기준

- W3 이전에는 LLM·NPU·새 임베딩 모델을 추가하지 않는다.
- A/E의 기본 선택이 끝나면 작은 점수 차이를 위해 새 검색 조건을 계속 늘리지 않는다.
- FR-04를 살리기 위한 분류표·기준기간 조사가 사용자 흐름을 계속 지연시키면 보류 사유를 남기고 독립 작업으로 분리한다.
- 상세 비교가 불가능한 이유가 제목 정보 부족이면 제목을 LLM으로 늘리지 않는다.
- 사용자에게 가치가 불명확하면 기능 수를 늘리기 전에 작업 흐름과 실제 근거를 점검한다.

## 20. 필수 테스트와 인수 기준

기존 검색·감사·보안 테스트를 보존한다. 아래 항목은 추가되거나 변경 범위를 검증할 테스트다. 기존 동등 테스트가 있으면 재사용한다. 특정 테스트 개수를 달성하는 것이 목표는 아니다.

| ID | 시험 | 통과 조건 |
|---|---|---|
| W-T01 | 요소 없이 최초 검색 | 원래 질의로 검색되고 필수 요소 입력을 강요하지 않음 |
| W-T02 | 방법·대상 관점 입력 부족 | 해당 관점만 안내·보류, 원래 검색 가능 |
| W-T03 | 실제 검색문 확인 | 사용자에게 보인 effective query와 엔진 입력이 같음 |
| W-T04 | 관점 전환 | 클릭한 관점만 실행, 자동 fan-out·fusion 없음 |
| W-T05 | 다른 관점의 점수 | 실행별 보존, 질의 간 점수 평균·기회점수 생성 없음 |
| W-T06 | 메타데이터 필터 | 필터를 만족하는 대상에서 후보·재정렬 |
| W-T07 | 재정렬 실패 | A fallback의 실제 엔진·경고 표시, E 성공으로 기록하지 않음 |
| W-T08 | 미확정 `tau` | 검색·비교·메모는 가능, 전체 관련 집계는 제한 유지 |
| W-T09 | 비교함 중복 | 동일 스냅샷·레코드는 한 번 선택, 여러 검색 출처 보존 |
| W-T10 | 필터·관점 변경 | 기존 선택 유지, 현재 결과 밖 항목을 구분 |
| W-T11 | 연구주제·요소 변경 | 초기화 확인 또는 revision 갱신, 오래된 판단 stale |
| W-T12 | 원문 표현 발견 | 정확한 구절·offset·원문 해시 확인 |
| W-T13 | 복합 요소 부분 일치 | 일부 단어만으로 전체 요소 확인 판정하지 않음 |
| W-T14 | 부정·비교 문맥 | 문자열 발견을 방법 사용·동일 연구로 자동 서술하지 않음 |
| W-T15 | 표현 미검출 | 자동 needs_review, 실제 연구 부재 판정 없음 |
| W-T16 | 사용자 확인 | 판단 주체와 의견을 분리, 원문 사실로 자동 승격 없음 |
| W-T17 | 가짜·변경된 인용 | 검증 실패·재검토 표시, 확정 메모에서 제외 |
| W-T18 | 다음 작업 생성 | 실제 사용자 요소·선택 근거만 사용, 실행 전 확인 |

## 21. 실행·보안·산출물 관리

### 21.1 기존 환경 유지

설치 명령을 실행하기 전에 현재 `pyproject.toml`, 가상환경, CLI `--help`, 앱 진입점을 확인한다. 이미 동작하는 torch·CUDA·모델 캐시를 본 명세만 보고 교체하지 않는다.

윈도우·리눅스의 경로와 공백·한글 폴더명을 지원한다. 개발자 개인의 절대 경로나 특정 서버 이름을 소스 코드에 고정하지 않는다. 서버의 다른 작업을 종료하거나 불필요한 캐시·중복 파일을 정리하는 작업은 별도 승인 없이 하지 않는다.

### 21.2 실행 가이드에 남길 것

실제로 확인한 명령만 README 또는 기존 실행 문서에 적는다.

```text
가상환경 선택
필요한 기존 의존성 설치/확인
기존 doctor 및 artifact 검증
실제 앱 진입점으로 localhost 실행
A/E 실제 엔진과 모델·데이터 확인
검색 → 관점 변경 → 비교 → 메모 실데이터 smoke
네트워크 차단 상태의 로컬 실행 확인
종료·세션 정리
```

`app.py`가 실제 진입점으로 확인된 경우의 실행 형태는 다음과 같다. 경로를 확인하지 않고 실행 성공을 보고하지 않는다.

```bash
python -m streamlit run app.py --server.address 127.0.0.1
```

### 21.3 개인정보·외부 전송

- 모델과 인덱스 준비 후 기본 질의·비교·메모 경로에서 외부 추론을 호출하지 않는다.
- 원본 데이터의 개인정보와 사용자 미공개 연구주제는 별도 취급한다. 공개 과제 데이터라는 이유로 사용자 질의도 공개 가능하다고 간주하지 않는다.
- API 키, SSH 개인키, 토큰, 비밀번호, 개인정보가 포함된 신청서·메일은 저장소·로그·내보내기에 넣지 않는다.
- 외부 페이지는 사용자가 출처 링크를 여는 동작과 서버가 질의를 전송하는 동작을 구분한다. 자동 외부 검색을 몰래 붙이지 않는다.
- 공용·인터넷 서비스로 배포하지 않는다. 연구실 서버가 필요하면 승인된 접근 경로와 계정·포트만 사용한다.

### 21.4 출력 안전

사용자·원문 텍스트를 그대로 실행 가능한 HTML로 렌더링하지 않는다. Markdown 인용·표의 특수문자를 escape하고 URL 스킴을 제한한다. CSV 내보내기는 기존 수식 실행 방지 정책을 유지한다.

메모 다운로드는 앱 메모리에서 파일 바이트를 생성하는 방식으로 가능하다. 자동 서버 파일 저장이 필요한 것처럼 구현하지 않는다. 파일 생성이 필요한 경우에도 사용자 명시 요청, 안전한 경로, 덮어쓰기 방지 정책을 적용한다.

> 기존 Research Compass 저장소를 유지하면서 이 문서를 적용하라. 먼저 최신 handoff, decisions, 데이터·모델 manifest, capabilities, 검색 평가 상태를 확인하고 기존 구현과 변경 대응표를 작성하라. 이미 완료된 감사·모델 설치·검색 구현을 처음부터 반복하지 마라.
>
> 사용자 흐름은 ‘원래 주제 검색 → 필요할 때 관점과 실제 검색문 수정 → 과제 선택 → 제목 근거 비교 → 다음 확인사항을 포함한 탐색 메모’다. 기본 버전은 사용자 수동 입력·선택, 기존 검색 엔진, 원문 문자열 근거, 템플릿으로 구현하라. LLM·NPU·새 검색 모델·자동 다중 검색을 추가하지 마라.
>
> A/E의 진행 중 평가를 마무리하되 UI 구현의 선행 조건으로 두지 마라. E가 미검증이면 A로 진행하라. LLM 라벨과 사람 라벨을 분리하고, 결과를 본 평가 분할은 최종 미사용 검증으로 오인시키지 마라. 증분 라벨과 키가 덮어쓰이거나 잘못 연결되지 않는지 점검하라.
>
> `tau` 확정과 D2·분류표 미해결 문제는 순위 기반 검색·비교·메모를 막지 않는다. 단, 그 검증이 필요한 전체 관련 집계·추세·저빈도 후보의 기존 게이트는 유지하라. ‘다음 탐색·확인’을 원래 FR-04 완료로 보고하지 마라.
>
> 제목에 표현이 있다는 사실과 실제 연구방법·성과를 구분하라. 미언급을 부재·신규성·기회로 해석하지 마라. 비교표의 인용은 원문 위치까지 검증하고, 사용자 해석과 자동 발견을 구분하라. 최종적으로 실제 검색·부분 관련·근거 부족 사례의 메모, 테스트 결과, 제한 기능, 실제 실행 명령을 인계하라.
