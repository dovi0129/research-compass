# Research Compass 구현 명세

> 문서 버전: 1.0  
> 대상: 구현 워커 에이전트 및 통합 담당자  
> 문서 성격: 제출 사업계획서 기반의 MVP 구현 계약  
> 일정 표현: 달력 날짜 없이 작업 의존성과 완료 조건으로만 정의  
> 기본 구성: 공공데이터 + 임베딩 의미검색 + 통계분석 + 웹 대시보드  
> 생성형 LLM/sLLM: 기본 범위에서 제외. 별도 승인 시 설명 보조 기능으로만 추가.

---

## 0. 워커에게 주는 실행 지침

이 문서를 읽고 **실제 데이터에서 확인되는 범위 안에서** Research Compass를 구현한다. 명세에 적힌 기능을 구현했다는 이유만으로 실제 데이터에서도 검증되었다고 보고하지 않는다.

1. 기존 저장소와 실행 환경을 먼저 확인한다. 기존 파일, 실행 중인 서비스, 다른 사용자의 GPU 작업을 임의로 변경하지 않는다.
2. `G0 환경 확인 → G1 데이터 감사 → G2 검색 → G3 분석 → G4 UI 통합 → G5 검증·인계` 순서로 진행한다.
3. 데이터의 실제 컬럼·집계 단위·기간·결합 가능성을 확인하기 전에 관련 기능을 확정하거나 가짜 데이터로 대체하지 않는다.
4. 기능은 작은 단위로 구현하고 테스트한다. 기능별 상태를 `구현`, `실데이터 검증`, `자료 부족`, `미구현`으로 구분한다.
5. sLLM 설치, 파인튜닝, 외부 유료 API, 공개 서버 배포부터 시작하지 않는다.
6. 스키마 변경, 데이터 추가, 모델 교체 등 핵심 변경은 근거와 영향을 남긴다. 사업계획서의 내용을 임의로 수정하지 않는다.
7. 최종 응답에는 실행 명령, 테스트 결과, 생성 파일, 남은 제약, 다음 작업을 기록한다. 실행하지 않은 작업을 완료로 표시하지 않는다.

**첫 번째 구현 결과물은 화면이 아니라 `reports/data_audit.md`다.** 단, UI 담당자는 감사와 병행하여 명확히 표시된 테스트 fixture로 화면 골격을 만들 수 있다.

## 1. 근거와 설계 결정의 구분

### 1.1 제출 문서에서 확인되는 사항

기준 문서: `아이디어 기획 사업 계획서.hwpx`의 최종 제출본. 프로젝트명은 **Research Compass: 공공 연구데이터 기반 AI 연구기회 탐색 및 연구주제 의사결정 지원 서비스**다. [S1]

| 제출계획서의 항목 | 제출안에 적힌 내용 | 이 명세의 대응 |
|---|---|---|
| 활용 공공데이터명 | 한국연구재단_이알앤디_과제정보, 한국연구재단_선정과제 연구분야 | 두 데이터의 별도 수집·정제·출처 관리 |
| 공공데이터 활용방안 | 임베딩을 통한 의미 유사도 계산, 유사 연구과제 탐색 | FR-01 |
| 공공데이터 활용방안 | 관련 연구분야 분석 | FR-02 |
| 공공데이터 활용방안 | 연구지원 추세 분석 | FR-03: 데이터 범위 확인 후 제한적으로 제공 |
| 공공데이터 활용방안 | 상대적으로 탐색이 적은 인접 연구영역 탐색 | FR-04: 근거가 충족될 때만 후보 제공 |
| 아이디어 실현가능성 | 공개 임베딩 모델, 벡터 검색, 웹 대시보드 | 모듈형 Python 애플리케이션 |
| 개요·차별성 | 연구공백을 단정하지 않고 근거를 함께 제공 | 출처 표시, 판단 보류, 표현 제한 |

제출안에 **생성형 LLM/sLLM의 배포·운영을 하겠다는 명시는 없다.** 생성형 AI와의 비교 문구는 있지만, 이것을 LLM 구축 의무로 해석하지 않는다. [S1]

### 1.2 이 문서에서 새로 정하는 사항

아래는 제출서식에 적혀 있던 사실이 아니라 **구현을 위한 설계 결정**이다.

- 기본 모델·검색기·UI 선택, 모듈 경계, 내부 데이터 스키마.
- 검색 결과 수, 테스트 방법, 설정 파일, 오류 처리와 완료 조건.
- 데이터가 부족할 때 기능을 제한하는 규칙.
- 후보를 제시하기 위한 검증 절차 및 규칙 기반 설명.

본 문서는 **데이터 등록 페이지와 공식 기술 문서를 참고했지만 실제 CSV 다운로드·전체 행 검사·서버 실행은 수행하지 않은 상태에서 작성된 명세**다. 원시 데이터와 실행 환경은 워커가 확인해야 한다. 모델 성능, 처리시간, 데이터 결합 가능성을 검증 완료로 간주하지 않는다.

### 1.3 앞선 구상에서 확정 사항으로 가져오지 않을 것

- 데이터 행 수를 고정 상수로 사용하지 않는다.
- 과제 데이터에 연구분야 코드, 초록, 고유 과제번호가 반드시 있다고 가정하지 않는다.
- 분야별 선정 통계와 과제 목록을 바로 조인할 수 있다고 가정하지 않는다.
- 검색 상위 몇 건의 연도 분포를 전체 연구지원 추세로 해석하지 않는다.
- 선정횟수가 적다는 이유만으로 유망성·독창성·지원받을 가능성이 높다고 판단하지 않는다.
- 코사인 유사도를 정답 확률이나 백분율 정확도로 표시하지 않는다.

이 항목들은 제출안의 방향을 바꾸기 위한 것이 아니라, **구현 시 확인되지 않은 가정을 사실처럼 만들지 않기 위한 제한**이다. 제한으로 인해 제출안의 일부 기능이 실데이터에서 동작하지 않으면 이를 별도로 보고한다.

## 2. 제품 목표와 범위

### 2.1 목표

사용자가 연구주제를 자연어로 입력하면 다음을 확인할 수 있는 웹 MVP를 만든다.

1. 입력 주제와 의미적으로 가까운 실제 공개 연구과제.
2. 입력 주제와 가까운 연구분야 및 원자료에 있는 선정 현황.
3. 수록 데이터 범위 내에서 계산한 연도별 분포와 해석 제한.
4. 조건이 충족되는 경우, 추가 검토할 인접 분야와 그 근거.

서비스의 목적은 **연구자의 탐색을 돕는 것**이다. 학문적 신규성 판정, 전 세계 연구공백 탐지, 과제 선정 가능성 예측을 제공하지 않는다.

### 2.2 사용자와 주요 시나리오

주요 사용자: 대학원생, 신진연구자, 새로운 분야를 탐색하는 연구자. [S1]

대표 흐름:

`연구주제 입력 → 유사 과제 확인 → 관련 분야와 수록 현황 확인 → 추가 검토 후보 확인 → 근거 데이터 열람·결과 저장`

입력 예시:

- 제조공정에서 강화학습을 활용한 에너지 최적화
- 산업 전력 사용 데이터의 이상탐지
- 양자배터리 충전 성능과 제어

위 문장은 **테스트 입력 예시**다. 해당 주제의 관련 과제가 실제 데이터에 있다는 보장은 하지 않는다.

### 2.3 기본 범위

- 두 공공데이터 파일의 등록, 감사, 정제 및 출처 추적.
- 과제 의미검색과 비교용 어휘 기반 검색.
- 연구분야의 독립적인 의미검색 및 선정 통계 표시.
- 연도별 수록 분포와 조건부 추세 분석.
- 근거 조건부 연구기회 후보 로직과 규칙 기반 설명.
- Streamlit 웹 화면, 결과 내보내기, 실제 데이터 검증 보고서.
- 인터넷이 끊겨도 준비된 로컬 자료로 실행 가능한 기본 경로.

### 2.4 기본 범위 밖

회원가입, 사용자별 장기 이력, 결제, 모바일 앱, 관리자 시스템, 자동 주기 수집, 분산 벡터 DB, 자체 모델 학습, 파인튜닝, 자동 논문 작성, 지원사업 합격 예측, 공개 인터넷 서비스 운영은 구현하지 않는다.

sLLM, 재정렬 모델(reranker), 외부 논문·특허 데이터 연계는 **별도 확장**이다. 기본 기능의 완료를 막지 않아야 하며 승인 없이 범위를 늘리지 않는다.

## 3. 전체 구조와 기술 선택

### 3.1 처리 경로

```text
[사전 처리]
공식 CSV 원본 2종
    → 원본 해시·메타데이터 기록
    → 데이터 감사·컬럼 매핑·정제
    → 과제 임베딩 / 분야명 임베딩
    → 인덱스·메타데이터·기능 가용성 저장

[실행 시]
사용자 연구주제
    → 입력 검증·동일 모델로 질의 임베딩
    ├─ 과제 검색 → 전체 필터 대상 점수 → 상위 결과 + 연도별 분포
    └─ 분야 검색 → 원문 선정 현황 → 조건부 추가 검토 후보
    → 규칙 기반 설명·출처·한계 표시
    → Streamlit 대시보드 / 결과 JSON·CSV

[선택적 확장]
확정된 검색·분석 결과 → sLLM 설명 보조
```

두 데이터는 기본적으로 **나란히 분석한다.** 동일 과제 식별자와 분야 매핑 근거가 확인되기 전에는 과제와 분야 통계의 행 단위 직접 결합을 수행하지 않는다.

### 3.2 기본 스택

| 구성 | 기본 선택 | 구현 방침 |
|---|---|---|
| 언어 | Python | 독립 가상환경. 실제 설치·검증한 버전을 고정 |
| 데이터 | pandas + NumPy | 원본 보존, 정제 결과 별도 저장 |
| 임베딩 | `BAAI/bge-m3`의 dense embedding | 출발점으로 선택. 이 과제에서 최고 성능이라고 가정하지 않음 |
| 임베딩 실행 | sentence-transformers | 모델 카드의 지원 경로를 참고하고 실제 revision 고정 |
| 벡터 검색 | FAISS `IndexFlatIP` | 정규화된 벡터로 정확 검색 |
| 참조 구현 | NumPy 행렬 내적 | 검색 결과 검증과 FAISS 설치 실패 시 명시적 대체 경로 |
| 비교 검색 | 문자 n-gram TF-IDF | 복잡한 형태소 분석기 없이 비교 기준 확보 |
| UI | Streamlit | 기본적으로 단일 Python 프로세스 |
| 차트 | Streamlit 기본 차트 또는 Plotly | 추가 선택은 설치·유지 부담이 작은 쪽으로 고정 |
| 테스트 | pytest | fixture 기반 단위 테스트 + 별도 실데이터 테스트 |

BGE-M3의 모델 카드는 sentence-transformers를 통한 dense embedding 사용 경로를 제공한다. FAISS는 질의·문서 벡터를 모두 정규화한 inner product 검색으로 코사인 검색을 구현하는 방법을 설명한다. [T1][T2]

### 3.3 실행 환경 원칙

- 연구실 서버의 실제 GPU 종류·메모리·사용 가능 여부는 환경 점검에서 확인한다. 특정 서버 사양을 전제로 코드를 작성하지 않는다.
- GPU는 인덱스 생성과 질의 임베딩 가속에 사용할 수 있지만, GPU 전용 벡터 DB나 LLM 서버를 필수로 만들지 않는다.
- 장치 선택은 설정값으로 한다. OOM 발생 시 배치 크기를 줄이고 원인을 보고한다. 다른 작업을 종료하지 않는다.
- 시스템 CUDA, 공용 Python, 방화벽, 기존 포트를 임의로 변경하지 않는다.
- 준비된 모델과 인덱스가 있으면 실행 중 외부 API 호출 없이 동작하도록 한다.

## 4. 데이터 원천과 최우선 확인사항

### 4.1 D1: 연구과제 정보

- 명칭: `한국연구재단_이알앤디_과제정보`
- 데이터 식별자: `3049029`
- 등록 페이지: `https://www.data.go.kr/data/3049029/fileData.do`
- 용도: 과제명 의미검색, 사업·기관 필터, 연도별 수록 분포. [D1]

공식 등록 페이지의 컬럼 안내에는 사업년도, 선정년도, 사업명 계층, 과제명, 연구책임자명, 연구자번호, 주관기관명, 보안과제여부가 나온다. **이 안내에서 초록·연구분야 코드·고유 과제번호는 확인되지 않는다.** 실제 CSV의 컬럼이 최종 판단 기준이다. [D1]

### 4.2 D2: 연구분야 선정 현황

- 명칭: `한국연구재단_선정과제 연구분야`
- 데이터 식별자: `15120687`
- 등록 페이지: `https://www.data.go.kr/data/15120687/fileData.do`
- 용도: 분야명 의미검색, 분야별 원문 선정횟수, 조건부 비교. [D2]

등록 페이지는 과학기술표준명, 중심분야코드, 연도가 붙은 선정횟수 항목을 안내한다. **페이지 설명문의 기준연도와 컬럼명의 연도 표기가 서로 다르므로, 기준기간을 확정하지 않고 구현을 진행하면 안 된다.** 이 명세는 두 표기를 임의로 조정하지 않는다. [D2]

### 4.3 데이터 획득 규칙

1. 공식 페이지에서 허용되는 다운로드 방법으로 원본을 확보한다. URL 자체를 CSV 다운로드 주소라고 가정하지 않는다.
2. 파일명이 아니라 실제 내용·인코딩·헤더를 검사한다. HTML 오류 페이지를 CSV로 받아들이지 않는다.
3. API를 사용한다면 실제 활용승인과 엔드포인트를 확인한다. 임의의 API 주소를 생성하지 않는다.
4. 접근에 실패하면 확보한 정보와 필요한 입력 파일을 보고한다. 비공식 데이터로 조용히 대체하지 않는다.
5. 원본 파일은 수정하지 않는다. `data/raw/` 아래에 보존하고 해시를 남긴다.
6. 기본 구현은 CSV를 로컬에 확보한 뒤 실행한다. 자동 갱신·API 의존 실행은 후속 범위다.

### 4.4 데이터 감사 체크리스트

`reports/data_audit.md`에는 최소 다음을 기록한다.

| 점검 | 확인할 내용 | 실패 시 처리 |
|---|---|---|
| 출처·스냅샷 | 데이터 ID, URL, 파일명, 실제 확보시각, SHA-256 | 추적 불가 파일을 실제 데이터 검증에서 제외 |
| 형식·인코딩 | CSV 여부, 인코딩, 구분자, 원본 컬럼 | 읽기 오류를 숨기지 말고 중단 |
| 규모 | 원본 행 수, 유효 행 수, 제외 행 수 | 고정 예상 행 수에 억지로 맞추지 않음 |
| 제목·분야명 | 결측, 공백, 마스킹, 깨진 문자열 | 검색 불가 행을 격리하고 이유 기록 |
| 행 단위 | 한 행의 의미, 반복 수록·계속과제 여부 | 과제 수 대신 레코드 수로 명칭 제한 |
| 중복 | 완전 동일 행과 제목만 같은 행 구별 | 제목만 같다는 이유로 삭제하지 않음 |
| 연도 | 사업년도와 선정년도의 의미, 실제 범위 | 두 연도를 혼용하지 않음 |
| 분야 통계 | 선정횟수 컬럼명·단위·기간·결측 의미 | 미확인 항목은 비교 및 후보 생성에서 제외 |
| 분야 체계 | 코드 수준, 상·하위 분야, 중복 집계 여부 | 서로 다른 수준의 수치를 직접 비교하지 않음 |
| 데이터 연결 | 공통 식별자, 공식 매핑, 기간 일치 | 근거 없으면 독립 검색 유지 |
| 공개 범위 | 원문 이용 조건, 보안 표시·민감 식별자 | 필요한 공개 필드만 사용 |

**페이지의 갱신 시각은 데이터의 관측기간이 아니다.** 실제 확보시각·게시정보·관측기간은 각각 별도 필드로 관리한다.

### 5.3 원본·정제·검색 데이터의 관계

- 원본 파일, 정제 데이터, 제외 행과 사유를 각각 보존한다.
- 완전 동일 행은 검색 표시 중복을 줄이기 위해 묶을 수 있지만, 원본 행 수와 그룹 크기를 보존한다.
- 제목만 같은 행, 기관·사업·선정연도가 다른 행을 임의로 같은 과제로 합치지 않는다.
- 공식 식별자가 없으면 독립 과제 수를 확정하지 않는다. 집계 명칭은 `수록 레코드 수` 또는 `정제 후 고유 레코드 수`로 한다.
- 코드·연도·개수의 파싱 실패는 조용히 버리지 말고 감사 보고서에 기록한다.
- 연구자번호, 신청서의 전화번호·학번·서명 등은 임베딩·화면·결과 파일에 넣지 않는다. 신청서 개인정보는 서비스 데이터가 아니다.
- 보안 표시가 있는 행은 기본 제외하고 제외 근거를 기록한다. 표시값의 의미가 불분명하면 확인 전 임의로 공개 가능으로 판정하지 않는다.

## 6. FR-01 — 유사 연구과제 탐색

### 6.1 입력

- 자연어 연구주제 `query`.
- 선택 필터: 선정년도 범위, 사업명, 주관기관. 실제 제공 필드만 노출한다.
- 화면 결과 수 `top_k`: 기본 10, 허용 1~50.
- 공백 제거 후 2~500자 입력을 받는다. 이는 초기 UI 제한이며 모델의 토큰 한도와 다르다.

모델 토큰 한도를 별도로 검사한다. 과도한 길이는 안내 후 재입력을 요청하거나, 명시적으로 표시한 절단 정책을 사용한다. 조용히 중요한 뒷부분을 자르지 않는다.

### 6.2 문서 텍스트

기본 `search_text = title_normalized`로 시작한다. 기관명·연구책임자·식별번호는 임베딩에서 제외한다.

사업명 추가는 별도 비교 실험에서 유효할 때만 채택한다. 사업명이 비슷하다는 이유로 기술적으로 무관한 과제가 상위에 오르는지 확인한다. 선택한 텍스트 구성을 manifest에 기록한다.

제목만 제공된 과제에 대해 연구방법·실험결과·성과·한계를 추정해서 문서 텍스트에 보충하지 않는다.

### 6.3 임베딩·검색

1. 문자열을 Unicode 정규화하고 연속 공백을 정리한다. 기술 용어·숫자·기호를 무차별 삭제하지 않는다.
2. 고정된 모델 revision으로 배치 임베딩한다.
3. 문서와 질의 벡터를 모두 L2 정규화한다.
4. 정규화 벡터 내적을 사용해 높은 점수부터 반환한다. [T2]
5. 메타데이터 필터를 먼저 적용한 검색 집합을 기준으로 순위를 계산한다.
6. 동점은 `record_id`로 안정적으로 정렬한다.

원형:

```text
score(q, d) = normalized_embedding(q) · normalized_embedding(d)
```

MVP의 정확성 기준은 전체 대상 벡터에 대한 내적이다. FAISS 결과를 NumPy 참조 구현과 비교한다. 필터를 적용하기 전에 전역 Top-K만 구한 뒤 결과를 잘라내는 방식은 사용하지 않는다.

### 6.4 관련도 점수와 판단 보류

- UI 표기: `의미 유사도 0.XXX`. `일치 확률 XX%`, `정확도 XX%`라고 쓰지 않는다.
- 과제 점수와 분야 점수에 같은 관련도 기준을 자동 적용하지 않는다.
- 관련도 기준값 `tau_project`는 개발 질의의 사람 평가로 정한다. 근거 없이 상수로 고정하지 않는다.
- 기준값 미검증 상태에서도 `가까운 검색 결과`는 보여줄 수 있지만 `관련성 검증 전`을 표시한다.
- 기준값 미검증 상태에서는 관련 과제 수·후보 생성에 이 점수를 확정된 분류 결과처럼 사용하지 않는다.
- 모든 결과가 기준 미달이면 `조건을 충족하는 관련 과제를 찾지 못함`으로 표시한다. 이것을 해당 연구가 없다는 증거로 설명하지 않는다.

### 6.5 반환 항목

각 결과는 `rank`, `record_id`, `title`, `semantic_score`, 가능한 원문 메타데이터, `source_snapshot_id`, 원본 행 위치, 원문 링크를 포함한다.

공식 과제 상세 URL이 없으면 데이터 등록 페이지와 원본 행 위치를 제공한다. `record_id`로 존재하지 않는 과제 상세 URL을 조합하지 않는다.

## 7. FR-02 — 관련 연구분야 분석

### 7.1 기본 방식

D2의 분야명 목록을 별도로 임베딩하고, 같은 질의로 관련 분야를 검색한다. 이는 **입력 주제와 분야명 사이의 모델 유사성**이며, D1의 각 과제가 그 분야에 공식 분류되었다는 뜻이 아니다.

UI에는 다음 문구를 표시한다.

> 관련 분야는 입력 주제와 공개 분야명 간 의미 유사도로 탐색한 결과이며, 개별 과제의 공식 분류를 뜻하지 않습니다.

### 7.2 선정 현황 표시

- 검증된 개수·단위·기간을 함께 표시한다.
- 기준기간 충돌이 해결되지 않으면 비교 차트·순위화를 중단한다. 원문 확인 영역에서만 원래 컬럼명과 `기간 확인 필요`를 보여줄 수 있다.
- 결측, 미집계, 공개 제한을 0회 선정으로 표시하지 않는다.
- 상위·하위 분류가 섞여 있으면 합계를 만들지 않는다.
- 신청 건수 분모가 없으면 선정률·경쟁률을 계산하지 않는다.
- 선정횟수는 지원 금액이나 연구성과가 아니다.

### 7.3 데이터 연결 정책

기본 `project_field_join = disabled`를 유지한다.

활성화하려면 공식 연결키, 매핑 출처, 다대다 관계, 기간 호환성, 연결 성공률·미연결률을 기록해야 한다. 분야명 임베딩의 가장 가까운 코드를 원문 과제의 공식 분야 코드로 저장하는 것은 금지한다.

## 8. FR-03 — 연도별 분포 및 조건부 추세 분석

### 8.1 기본 기능: 수록 레코드 분포

`선정연도별 수록 레코드 분포`를 제공한다. 이것이 기본 제공 수준이다.

관련도 기준이 검증되었다면, 화면 Top-K가 아니라 **현재 필터를 통과한 전체 레코드**에서 기준 이상인 레코드를 집계한다.

```text
C = 현재 메타데이터 필터를 통과한 전체 검색 레코드
R = {d ∈ C : score(q, d) ≥ tau_project}
count[y] = R 중 selection_year가 y인 레코드 수
```

화면의 Top-K를 5에서 10으로 바꿔도 `count[y]`는 달라지지 않아야 한다. 선정연도 미상 건수는 별도로 표시한다.

`tau_project`가 미검증이면 전체 관련 분포 기능은 보류한다. 선택적으로 `현재 표시된 검색 결과의 선정연도 구성`만 보여줄 수 있으며, 이를 추세 분석으로 표시하지 않는다.

### 8.2 표현과 분모

- 기본 차트 제목은 `다운로드한 자료 내 선정연도별 수록 분포`로 한다.
- 실제 전체 모집단을 대표한다는 근거가 없으면 국가 전체 연구지원 현황이라고 하지 않는다.
- 현재 사업연도에 수록된 계속과제의 과거 선정연도 분포일 수 있으므로, 선정연도만 보고 해당 연도의 신규 선정 건수를 확정하지 않는다.
- 관측되지 않은 연도를 0건으로 채우지 않는다. 같은 수집범위 안에서 기록이 없는 연도와 미수집 연도를 구분한다.
- 비율을 제시한다면 분모와 필터를 함께 기록한다. 비율도 원본의 대표성 문제를 해결하지는 않는다.

### 8.3 추세 해석 활성화 조건

`comparable_trend`는 다음이 모두 확인된 경우에만 활성화한다.

- 각 기간이 무엇을 집계하는지 명확하다.
- 기간별 대상 사업·과제 포함 기준이 비교 가능하다.
- 반복 수록과 계속과제 처리 방법이 명확하다.
- 불완전한 기간과 결측기간이 구분된다.
- 분석에 필요한 기간 수가 실제 확보되어 있다.

근거가 없으면 `증가하는 유망 분야`, `최근 성장률` 같은 문구를 출력하지 않는다. 이때 인계 보고서에는 **제출안의 추세 기능은 제한적으로 구현됨**이라고 명시한다.

## 9. FR-04 — 근거 조건부 연구기회 후보

### 9.1 기능 정의

화면 명칭: **연구기회 후보 — 추가 검토할 인접 분야**.

입력 주제와 관련된 분야 중, 비교 가능한 공개 선정 통계에서 상대적으로 적게 나타나는 분야를 추가 탐색 대상으로 보여준다. 후보의 의미는 **탐색 순서 보조**이지, 신규성·유망성·성공 가능성의 판정이 아니다.

이 기능은 제출안의 핵심에 포함되므로 단순히 선택 기능으로 밀어두지 않는다. 다만 **조건이 부족하면 후보를 억지로 채우지 않는 동작까지 구현 범위**에 포함한다. [S1]

### 9.2 초기 규칙

다음 값은 연구적으로 검증된 기준이 아니라 **초기 프로토타입의 설계값**이다. 설정에 노출하고 개발 데이터로 점검한다.

- 관련 분야 검토 풀: 최대 20개.
- 분야 관련도 기준: `tau_field`, 개발 질의로 별도 검토.
- 비교 가능한 관련 분야 최소 수: 5개.
- 낮은 선정횟수의 초기 기준: 비교 집단의 하위 25% 값 이하.
- 최종 표시 후보: 최대 3개.

처리 순서:

1. D2 분야명 전체에서 질의와의 의미 유사도를 계산한다.
2. `tau_field` 이상인 분야를 추린다. 기준이 미검증이면 후보 생성은 비활성화한다.
3. 비교 기간·집계 단위·분류 수준이 일치하는 `comparison_group_id`별로 나눈다.
4. 선정횟수가 검증된 분야만 비교 집단으로 사용한다.
5. 각 집단에서 관련도가 높은 최대 20개 분야를 취하고, 5개 미만이면 그 집단의 후보를 생성하지 않는다.
6. 해당 비교 집단의 선정횟수 하위 25% 값을 선형 보간(`linear`) 방식으로 계산한다. 개수의 변동이 전혀 없으면 낮은 분야를 구분하지 않는다.
7. 조건을 만족한 분야를 관련도 순으로 정렬하고, 동일 분야의 중복을 제거한 뒤 전체 최대 3개를 보여준다.
8. 후보마다 비교 집단·기간·개수·기준·한계를 같이 표시한다.

동률이 많으면 하위 25% 기준을 만족하는 분야 비율이 25%를 넘을 수 있다. 실제 비교 대상 수와 기준값을 표시하고 이를 숨기지 않는다. 코드 앞자리가 같다는 이유만으로 비교 집단을 만들지 않는다.

### 9.3 후보의 출력 계약

각 후보에 다음 필드를 포함한다.

```text
field_record_id / field_name
query_similarity
selection_count / period_label / count_unit
comparison_group_id / comparison_size
comparison_cutoff / rule_version
reason_text
source_dataset_id / source_snapshot_id / source_row_numbers
limitations
```

`reason_text`는 코드가 계산한 값으로 만든 템플릿을 사용한다.

> 입력 주제와 의미적으로 관련된 분야입니다. 확인된 동일 비교조건에서 선정횟수가 상대적으로 낮아 추가 검토 대상으로 표시했습니다. 선정횟수가 낮다는 사실은 연구공백이나 연구 가치가 높다는 뜻이 아닙니다.

이 설명에 실제 수치·기간·비교 집단을 붙인다. 원문 과제와 연결키가 없으면 후보의 근거로 D1 특정 과제를 임의 연결하지 않는다.

### 9.4 판단 보류

다음 중 하나면 후보 대신 사유를 출력한다.

- 관련도 기준 미검증.
- 분야 통계의 기간·단위 충돌.
- 비교 가능한 관련 분야 부족.
- 모두 결측이거나 비교 집단의 값이 동일함.
- 신뢰할 수 있는 비교 집단 정의가 없음.
- 입력과 충분히 관련된 분야를 찾지 못함.

문구 예시:

> 현재 공개 데이터와 비교 조건으로는 연구기회 후보를 신뢰성 있게 제시하기 어렵습니다. 관련 과제와 분야 검색 결과를 참고해 추가 검토해 주세요.

관련 분야 자체는 별도 영역에 계속 표시할 수 있다. **단순 관련 분야 목록을 연구기회 후보의 실데이터 검증 완료로 보고하지 않는다.**

### 9.5 금지하는 점수·추론

`관련도 × 신규성 × 성장성`과 같은 근거 없는 종합 기회 점수를 만들지 않는다. 낮은 선정횟수, 낮은 검색 밀도, 검색 무결과를 학문적 공백으로 바꾸지 않는다. 제목만으로 기존 과제의 구체적인 미해결 문제를 추정하지 않는다.

## 10. FR-05 — 근거 표시와 설명

### 10.1 기본 설명기

LLM 없이 템플릿과 실제 계산값으로 동작한다.

- 원문 과제명 또는 분야명.
- 원본 등록 페이지 링크.
- 스냅샷 식별자와 원본 레코드 위치.
- 통계 기간과 사용한 필터·관련도 기준.
- 자료 및 모델의 한계.

출처 링크가 있다는 사실만으로 설명의 내용이 참이 되는 것은 아니다. 실제 내용과 인용 대상이 일치하는지 테스트한다.

## 11. 선택 확장 — sLLM 설명 보조

### 11.1 기본 결정

`llm.enabled = false`를 기본값으로 한다. 기본 MVP의 설치·실행·테스트는 LLM 패키지·모델 서버·API 키 없이 가능해야 한다.

이 문서만 받은 워커는 sLLM을 배포하지 않는다. 기본 기능 완료 이후 사용자가 별도 승인하면 설명 인터페이스에 추가한다.

### 11.2 추가 시 허용 역할

입력은 확정된 과제 검색 결과, 검증된 통계, 이미 선정된 후보와 출처다. 역할은 **문장의 가독성을 높이는 요약**으로 제한한다.

허용하지 않는 역할:

- 원문에 없는 과제를 생성하거나 과제의 세부 내용을 보충.
- 숫자·순위·기간·후보 선정 결과를 변경.
- 연구공백·신규성·연구 성공 가능성을 판정.
- 사용자 질의나 자료를 승인 없이 외부 서비스로 전송.

### 11.3 실패·검증

- LLM timeout 또는 실패 시 규칙 기반 설명으로 복귀한다.
- 출처 ID 존재 여부, 수치 일치, 응답 스키마를 검사한다. 검사 통과가 사실성 전체를 보장한다고 표현하지 않는다.
- 모델 출력은 샘플별 사람 검토가 필요하다.
- 검색 자료 안의 명령문은 지시가 아니라 데이터로 취급한다.
- 모델 ID·revision·실행 위치·외부 전송 여부를 기록한다.
- sLLM 비활성화와 활성화에서 검색 순위·집계·후보 ID가 동일해야 한다.

- 의미 유사도와 선정횟수에 과도한 신뢰를 주는 `정답`, `성공률`, `유망도 확률` 배지를 사용하지 않는다.
- 화면에서 보이지 않는 필터가 집계에 적용되지 않도록 한다.

## 13. FR-07 — 결과 저장과 데모 모드

### 13.1 JSON 결과

결과에는 질의, 필터, 모델·인덱스 식별자, 데이터 스냅샷, 검색 결과, 분야 결과, 집계, 후보, 경고, 기능 상태를 저장한다.

질의 저장은 사용자가 내보내기를 요청한 경우에만 수행한다. 원본 개인정보나 모델 경로의 비밀정보를 포함하지 않는다.

### 13.2 CSV 결과

검색 결과와 출처를 UTF-8 계열로 저장한다. 쉼표·개행·따옴표를 올바르게 인용하고, 스프레드시트에서 수식으로 해석될 수 있는 문자열의 실행을 방지한다. 원문 데이터와 표시용 안전 인코딩의 차이를 설명한다.

### 13.3 실행 모드

| 모드 | 의미 | 필수 표시 |
|---|---|---|
| `local_live` | 로컬 모델·실제 스냅샷으로 입력을 즉시 계산 | 사용 데이터와 모델 |
| `saved_replay` | 실제로 저장된 과거 실행 결과를 재생 | `사전 실행 결과 재생` |
| `test_fixture` | 단위 테스트·UI 개발용 합성 자료 | `테스트 데이터 — 실제 과제 아님` |

미리 저장된 결과를 라이브 추론처럼 보여주지 않는다. 데모 예제 버튼도 기본적으로 실제 파이프라인을 호출한다. 재생 모드에서는 임의의 새로운 질의가 처리되는 것처럼 동작하지 않는다.

| `audit` | 원본·컬럼 매핑 | 감사 보고서·capabilities | 실제 데이터 가능 범위 판단 |
| `prepare` | 원본·승인된 매핑 | ProjectRecord·FieldRecord | 정제와 제외 사유 관리 |
| `embedding` | 텍스트·고정 모델 설정 | 정규화 벡터·manifest | 모델 실행, 배치·장치 관리 |
| `retrieval` | 질의 벡터·필터 | 과제·분야 점수와 순위 | 사실 설명 생성 금지 |
| `analytics` | 전체 검색 점수·메타데이터 | 검증 가능한 집계 | Top-K 표시와 독립 |
| `opportunity` | 분야 점수·검증된 통계 | 후보 또는 보류 사유 | 공식 연결 없는 과제 인용 금지 |
| `explanation` | 확정된 결과 | 템플릿 설명 | 기본 LLM 의존 없음 |
| `service` | SearchRequest | SearchResponse | 상태·오류·모듈 통합 |
| `ui` | 사용자 입력·응답 | 화면·다운로드 | 계산 중복 구현 금지 |

### 14.2 내부 호출

HTTP API는 기본 범위가 아니다. UI와 CLI는 같은 Python 서비스 함수를 사용한다.

```python
# 아래는 구현해야 할 인터페이스 계약이며 현재 구현된 코드가 아니다.
def search(request: SearchRequest) -> SearchResponse:
    ...
```

`SearchRequest`:

```text
query: str
filters:
  selection_year_min: int | null
  selection_year_max: int | null
  programs: list[str]
  institutions: list[str]
top_k: int
include_explanation: bool
```

`SearchResponse`:

```text
schema_version: str
request_id: str
query: str
filters: object
run_mode: local_live | saved_replay | test_fixture
model_manifest_id: str
index_manifest_id: str
source_snapshot_ids: list[str]
project_results: list[ProjectResult]
field_results: list[FieldResult]
year_analysis: SectionResult
opportunity_analysis: SectionResult
explanation: SectionResult
warnings: list[Warning]
latency_ms: object
```

공통 `SectionResult`:

```text
status: ok | empty | unavailable | error
scope: object
items: list[object]
reason_codes: list[str]
evidence_refs: list[object]
limitations: list[str]
```

`unavailable`은 자료나 검증 부족, `empty`는 조건을 검사했으나 결과 없음, `error`는 실행 실패다. `null`, 빈 목록, 0을 서로 대신 사용하지 않는다.

### 14.3 오류 코드

최소 오류/경고 코드:

`DATA_NOT_READY`, `INVALID_QUERY`, `MODEL_NOT_AVAILABLE`, `INDEX_MISMATCH`, `NO_ELIGIBLE_RECORDS`, `UNCALIBRATED_RELEVANCE`, `UNKNOWN_PERIOD`, `CONFLICTING_PERIOD`, `UNVERIFIED_JOIN`, `NONCOMPARABLE_COUNTS`, `INSUFFICIENT_COMPARISON_SET`, `NO_OPPORTUNITY_CANDIDATE`.

화면에는 사람이 이해할 수 있는 한국어 설명을, 로그에는 비밀정보가 없는 구조화된 코드를 기록한다.

## 18. 검색 및 후보 평가

### 18.1 평가 구성

초기 목표: 개발 질의 최소 5개, 별도 평가 질의 최소 10개. 이는 **소규모 탐색 평가의 작업량 기준**이며 통계적으로 충분한 검증이라고 주장하지 않는다.

- 한국어 전문 주제, 한·영 혼용, 동의어, 넓은 주제, 구체적 복합 주제를 포함한다.
- 빈 문자열·기호·무관한 내용 등은 검색 품질 평균과 분리된 실패/판단 보류 시험으로 다룬다.
- 관련도 기준과 모델·텍스트 구성은 개발 질의로만 조정한다.
- 평가 질의 결과를 본 뒤 기준을 바꾸면 기존 평가는 탐색 결과로 표시하고, 새로 고정한 설정의 평가를 별도로 기록한다.

### 18.2 사람 라벨

각 질의에서 임베딩 검색 Top-5와 어휘 검색 Top-5를 합친 중복 제거 결과를 섞어 평가한다. 가능하면 검색 방식·순위를 가린다.

| 라벨 | 의미 |
|---|---|
| 2 | 제공된 제목·메타데이터상 직접 관련 |
| 1 | 인접 주제이거나 일부 관련 |
| 0 | 관련 없음 |
| U | 제공된 정보로 판단 어려움 |

평가자는 원문에 없는 과제의 상세 내용을 상상해서 점수를 주지 않는다. `U`를 조용히 0으로 바꾸지 말고 건수와 처리 정책을 보고한다. 가능하면 두 명이 검토하고 불일치 처리 방법을 남긴다.

### 18.3 검색 지표

- 엄격 `P@5`: 라벨 2의 수를 5로 나눈 값. 검색 대상이 5개보다 적으면 분모를 그 대상 수로 하고 표시한다.
- 완화 `P@5`: 라벨 1 또는 2를 관련으로 본 같은 지표.
- `U`가 포함된 질의는 확정값 대신 상·하한 또는 미확정 상태로 보고한다.
- 별도로 기준값 적용 후 결과의 관련 비율과 질의별 결과 제공률을 보고한다. 적게 반환하여 관련 비율만 높이는 현상을 숨기지 않는다.
- 응답시간은 모델 최초 적재를 포함한 cold와 적재 후 warm을 분리한다.

질의별 결과와 전체 요약을 함께 저장한다. 전체 관련 과제를 완전히 라벨링하지 않았다면 코퍼스 전체 recall을 계산했다고 주장하지 않는다.

### 18.4 후보 평가

후보 규칙의 실행 정확성과 후보의 연구 가치를 분리한다.

실행 정확성 점검:

- 관련도 기준·기간·단위·비교 집단 조건 충족 여부.
- 원문 선정횟수와 출력 숫자 일치 여부.
- 실제 비교 기준으로 후보가 선택되었는지.
- 근거가 부족할 때 보류했는지.

사람 검토 질문:

- 입력 주제와 관계가 있는가?
- 추가 검토 대상으로 이해 가능한가?
- 근거보다 강한 주장을 하는가?
- 원문 근거와 한계를 사용자가 확인할 수 있는가?

이 검토 결과를 `연구공백 탐지 정확도`로 이름 붙이지 않는다. 실제 데이터에서 비교 조건이 충족되지 않으면 `실데이터 후보 평가 불가`라고 보고한다.

### 18.5 성능·효과 주장

처리시간, 검색 품질, 탐색시간 절감의 수치는 실제 측정 결과로만 기록한다. 사용성 실험을 수행하지 않았으면 연구시간 절감률을 작성하지 않는다. baseline보다 개선되지 않으면 그대로 보고하고 어휘 검색을 남긴다.

## 20. 운영·성능·안전 요구사항

### 20.1 재현성

동일 원본·설정·모델·인덱스에서 결과가 재현되어야 한다. CPU/GPU 수치 차이의 허용 오차와 순위 동률 정책을 문서화한다. 공개 모델의 `main`만 기록하지 말고 확보한 revision을 고정한다.

### 20.2 응답성과 자원

사용자 질의 때 전체 코퍼스를 재임베딩하지 않는다. 결과가 늦어지면 로딩 상태를 표시한다.

Warm 검색 응답의 초기 사용성 목표는 5초 이내로 두되, **지정 환경에서 측정해 판단할 목표일 뿐 보장값이 아니다.** 코퍼스 크기·장치·배치·cold/warm 구분과 함께 보고한다. 목표 미달이면 병목을 분석하고 UI·모델 적재·배치 설정을 개선한다.

### 20.3 접근 제어

기본 바인딩은 localhost다. 연구실 서버에 배포할 경우 사용자가 승인한 계정·포트와 SSH 터널 등 기존 접근 경로를 사용한다. 인증 없는 공개 포트 개방을 작업 완료 조건으로 삼지 않는다.

### 20.4 개인정보와 비밀정보

- 미공개 연구 아이디어를 외부 API로 보내지 않는 기본 경로를 유지한다.
- 사용자 질의와 개인 식별정보를 기본 로그에 남기지 않는다.
- API 키, 토큰, SSH 정보, 개인정보가 포함된 신청서 파일을 저장소에 넣지 않는다.
- 디버깅용 출력에도 원본 연구자번호 등 불필요한 필드를 포함하지 않는다.
- 원문과 모델의 이용 조건을 기록하되, 공개 데이터라는 이유만으로 모든 이용이 검토 없이 허용된다고 단정하지 않는다.
